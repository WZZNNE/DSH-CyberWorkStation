# 实施路线与决策记录

版本 0.1　设计日期：2026 年 9 月 15 日

## 1 交付边界与实施原则

本包提供研究、产品与架构设计、接口和数据库草案、有限参考验证。它不是已经运行的完整记忆平台。真实的 UI、认证、云端部署、DSH 全量适配、生产迁移、恢复保证和性能数据，都需要后续实现与验收。参考脚本即使通过，也只证明它覆盖的窄范围行为。

实施主线是先把变更正确地保存、检索与撤销，再增加模型自动整理和语义召回。第一版服务面向单用户、本机持久存储、多个项目和少量并发 agent；所有写入进入同一个权威服务。设计详见[产品与架构](01-产品与架构设计.md)，操作语义详见[使用与运维说明](03-使用与运维说明.md)。

已有研究和项目涉及版本、时效、撤销及记忆生命周期，不能把这些概念宣称为独创。研究贡献应落到可复现的机制组合、明确边界和实验证据，例如未来生效边界、旧任务恢复、防复活与实际副作用状态在同一评测中是否改善。

最新候选中 ReMe 已有 DSH 插件，EverOS、LongMemory、OpenClaw 已覆盖大量记忆治理能力。P0 必须先运行最相关候选的对照用例；满足核心契约时优先适配，后续阶段只补真实缺口。下表以需要自建权威模块的保守路径估工；若复用成功，应重估，不能机械照搬工期。ReMe 当前指南包含批量提交与仅根 agent 的默认选项，因此现成接入不等于已满足本方案的逐事件保存和子 agent 一致性要求。证据见[项目全景 P38](research/projects.md)。

## 2 阶段路线与退出条件

下表工时是假设一名熟悉 TypeScript、SQL 和 agent 框架的全职开发者，复用现有界面与库、无需训练模型、只支持一个宿主版本的初步估算。每周按有效开发时间估算，测试与文档在阶段内；不包含长期用户招募、供应商审批、跨平台疑难适配或正式安全审计。不是交付承诺，也不能直接相加视为排期。

| 阶段 | 交付内容 | 退出条件 | 粗估 |
|---|---|---|---|
| P0 范围与验证准备 | 确定数据边界、状态机、威胁模型、20–50 个典型中文/英文场景；梳理现有 DSH 行为；固定基线 | 每项关键保证可对应一个案例；哪些属于上下文遵守、哪些可由执行器强制已明确；不确定项有负责人 | 1–2 周 |
| P1 单用户权威服务 | TS 服务、SQLite 事务、项目身份、手工记忆、版本与时间、撤销/替换、幂等操作、HTTP、状态页骨架、全文查询 | 并发 v7→v8 冲突、相同键重试、未来生效、保存故障测试通过；没有 SQL 与文件双写权威；明确拒绝未知授权 | 3–5 周 |
| P2 可编辑管理与生命周期 | 来源/历史 UI、差异编辑、删除作业、outbox、索引重试、一致性备份及隔离恢复 | 用户能完成新增/查来源/撤销/冲突处理；删除后历史检索不可见；旧备份恢复不复活；故障注入后只承诺已提交记录恢复 | 3–5 周 |
| P3 DSH 接入与迁移 | 原生适配器、MCP 工具、上下文收据、旧 JSON 导入器、launcher 代理切换、独立运行检查 | 同项目新任务能使用当前规则；原型的普通编辑与删除也传播；迁移 dry-run 和 shadow 读校验通过；仅一个写入者 | 2–4 周 |
| P4 自动提取与可选向量 | 完整命题提案、来源定位、语义去重候选、中文分词、embedding 代际、检索融合与少量重排 | 否定/引用/提议/例外/未来生效均有标注评测；旧版本提取和向量结果被拒绝；离线降级可用；新增模型成本完整计入 | 3–5 周 |
| P5 多 agent 与恢复协议 | 可信任务范围、短期租约、单调 fence、撤销游标、受控动作入口、检查点核验 | 超时重复提交、过期子任务、撤销与动作竞争、未知副作用恢复等案例通过；明确记录网关覆盖和不能强制的动作 | 3–5 周 |
| P6 试点与差异验证 | 真实任务试点、用户操作测试、完整成本对照、公开可复现实验和限制 | 达到预先登记的接受阈值；失败案例公开分类；能说明复杂机制的实际收益；未达标部分删减或返回前一阶段 | 2–4 周 |

可用的本地 MVP 以 P1–P3 为核心，粗略范围约 8–14 周；更完整的自动整理与多 agent 试点通常需要数月，且工程人员熟悉度会显著影响估算。若只需验证核心生命周期，可先不做全量 UI、复杂向量索引和所有宿主，缩短到一个更小的研究原型。

退出条件是可验证的行为，不是“写完模块”。每阶段产出迁移说明、失败恢复说明及相关测试。某阶段达不到条件时，继续保持前一阶段可运行，不用额外堆服务掩盖核心问题。

## 4 memory.json 迁移方案

### 4.1 迁移前准备与 dry-run

不读取凭据，不以自动扫描全部聊天作为迁移前提。通过已有合法导出或用户选定文件获取 memory 数据，在副本上运行只读检查，展示条数、类型、范围、来源、过时状态、撤销记录、无效结构和潜在 ID 冲突。

建立映射：`legacy_store_id + legacy_item_id → memory_id`，使用 migration_id 去重。保留 createdAt、updatedAt、source、sessionId、meta、watermarks 与 withdrawals 的原始含义；迁移时间另记，不能把所有历史内容变成今天新说的要求。

cwd 通过可信项目映射转换成稳定 project ID；无对应项目的记录先待关联，不默认变全局。缺少原始证据的自动事实标注“历史导入，证据未核验”，不能升级成用户明确要求。原 JSON 数据可能已经被截断，迁移器不能声称恢复原始完整上下文。

dry-run 只输出差异和风险报告，不写目标权威库、不改源文件。具体命令在实现后写入安装文档，本设计不提供假想的已存在命令。

### 4.2 导入副本和 shadow 读

导入隔离目标库，校验数量、内容哈希、作用范围、来源映射、有效状态及撤销关系。旧向量可视为可重建索引；新模型不能直接使用不兼容向量。

shadow 读表示对经过授权的同一批查询，同时在旧实现与新实现检索，正式任务仍只收到原系统结果。比较新结果的适用性、漏召回、旧信息误用、延迟和 token 量；记录可解释差异，不要求新旧结果完全一致。

shadow 阶段新服务不接收独立的用户编辑作为正式权威写入。增量变化通过旧权威提交后形成的导入事件传播，使用稳定 ID/版本去重；若旧系统没有可靠变更日志，应采用短暂冻结写入和再次全量比对，而不是承诺无缝同步。

### 4.3 单写入切换

选择短维护窗口，暂停记忆编辑与自动写入，确认旧插件中在途提取/向量任务已结束或取消。导出最后一致状态，完成增量导入和验证，写切换记录与最终旧版本位置。

将 UI 和模型写工具指向新服务；关闭旧插件重复的长期记忆提取、注入和同名写工具。旧插件可继续承担 DSH 内部摘要查看/编辑，但相关长期记忆事件只由新适配器写一次。最后开放写入，并验证新建、编辑、撤销、跨任务召回和重启。

原文件保存为只读迁移证据或按保留策略处理。禁止多个 agent、旧插件和新服务分别直接编辑原 JSON，再期待按时间戳自动合并。

### 4.4 回退与再迁移

回退前暂停新变更，导出切换后全部事件、当前视图、撤销/删除信息及迁移映射，验证操作去重。可以先回退宿主适配器版本，同时继续保留新服务为存储权威，以减少数据格式回退风险。

如果必须切回旧存储，生成经核验的兼容视图。旧格式无法表达未来生效、条件例外或删除范围时，必须列出损失并阻止相关规则降级；可保持新服务只提供这些政策，或暂时停止依赖它们的任务。不能把不兼容规则平铺成普通 note 后声称语义保留。

不能简单复制迁移前的备份覆盖当前库；那会丢失新事件并可能复活已删内容。重新迁移时沿用稳定映射，保留所有后续撤销和删除屏障。

## 5 决策记录

以下 ADR 是本方案拟采用的技术决策，状态为“设计选择，待原型验证”，不表示仓库已按此改造。

### ADR-01 独立 TypeScript 服务，HTTP 与 MCP 共用业务层

**选择。** 独立进程拥有存储、事务和生命周期；HTTP 面向管理 UI 与可信宿主，MCP 提供少量模型工具。采用 TypeScript 与现有 DSH 生态一致。

**理由。** 服务可在 DSH 退出或容器重建后继续存在；客户端复用一致规则，降低两套接口行为不同的风险。MCP 工具不是全部产品能力，宿主仍需注入身份并管理上下文。

**代价。** 增加安装、进程监督、兼容版本与通信失败处理。第一版由明确的数据目录、健康状态和幂等请求控制复杂度，不立即引入多服务编排。

**重新评估条件。** 核心数据处理出现不可接受的运行时瓶颈，或选定数据库依赖在目标平台无法稳定部署；先测量再决定局部换语言。

### ADR-02 本地权威库采用 SQLite，集中控制变更

**选择。** SQL 保存原始事件引用、版本、关系、状态、收据和 outbox；主服务是唯一写入入口。使用 SQLite 本地文件，配置事务和持久化要求。

**理由。** 当前规模假设下部署简单，关系与版本可以在同一事务提交。禁止客户端直接打开跨机器共享数据库文件。

**代价。** 单写者和单机可用性限制，需要备份、恢复和明确的写入排队。直接文本编辑改为导入变更流程，牺牲随意覆盖文件的便利，换取可检测的冲突。

**重新评估条件。** 实测写入排队、恢复目标或高可用需求无法满足，再迁移 PostgreSQL；容量门槛由真实负载决定，不凭记录条数拍板。

### ADR-03 全文检索先行，向量可选

**选择。** SQL 精确过滤加 FTS5 提供默认查找；中文分词需要单独验证。向量是可重建索引，先允许小集合精确检索，sqlite-vec 等库锁定版本后再验证平台和过滤能力。

**理由。** 让本地无模型条件也可保存和查找；约束不依赖向量召回。初期能清楚测量 embedding 和重排带来的额外收益。

**代价。** 首版语义泛化有限；关键词不匹配可能漏召回。提供来源展开与改写查询，同时用基线测量缺口，不把加向量视为自动解决。

**重新评估条件。** 真实查询显示语义检索明显改善且成本可接受，再启用向量默认路径；多租户检索规模扩大时评估 pgvector 或独立向量服务。

### ADR-04 关系先用 SQL 表，不先部署图库

**选择。** 用明确的 `replaces`、`exception_to`、`derived_from`、`depends_on` 关系表达生命周期与证据依赖；查询先控制深度和结果预算。

**理由。** 当前最关键的是规则替换、例外与删除传播，不需要一开始自动构建通用知识图谱。关系与版本同事务写入更容易核验。

**代价。** 大规模多跳查询可能需要额外优化；关系抽取错误仍会影响结果。

**重新评估条件。** 消融证明多跳检索有稳定收益且关系表成为瓶颈时，再引入图服务作为查询投影；不能让它成为第二份独立权威。

### ADR-05 提取器提出变更，服务负责提交

**选择。** 模型输出带原文证据的结构化提案；服务验证身份、范围、来源、时间、目标版本与操作资格。明确、目标唯一的已授权变更自动提交；不确定内容保留 hypothesis 或待确认身份。

**理由。** JSON 格式正确不等于语义正确。正则可做格式处理，不负责判断撤销对象；隐藏思维链不作为存储证据。

**代价。** 需要可标注案例、语义校准和少量用户确认；纯模型自由写库更简单，但难以获得所需变更可靠性。

**重新评估条件。** 模型版本变化或新领域引起误设/误删升高，重新校准而非放宽全部校验。

### ADR-06 撤销、彻底删除和归档分别实现

**选择。** 撤销结束适用期；归档改变普通背景检索优先级；彻底删除先阻断读取，再清理服务控制的副本和备份。审计外壳尽量不含正文。

**理由。** 用户不再要求某行为，不等于要求禁止它，也不等于删除全部历史。删除操作必须可查看进度，恢复不能带回已删内容。

**代价。** 引入依赖清理、删除清单和备份期限；宿主或外部 provider 副本可能不在控制范围。

**重新评估条件。** 某些部署要求更强磁盘清除或加密密钥销毁，应独立定义并验证删除承诺，不能把普通 SQL delete 当成保证。

### ADR-07 当前约束单独编译，受控动作重新检查

**选择。** 约束路径按身份、范围和时间确定性加载；背景路径进行检索。收据记录版本与时效，租约/fence 约束恢复后的旧执行者。

**理由。** 单纯 top-k 检索和更新通知无法保证旧上下文不会指导下一次操作。未来生效时间也可能在没有新写入的情况下改变规则。

**代价。** 需要宿主和工具入口配合；风格等自然语言要求不能全部形式化，必须披露保证强度。动作已被接受或已发往外部后的取消只作尽力处理。

**重新评估条件。** 网关覆盖不足时降低宣称的保证范围；不要通过文字提示把未接入动作包装成受控动作。

### ADR-08 云端阶段使用 PostgreSQL，保持业务语义

**选择。** 云端、高并发多主机写入或高可用需求成立后再采用 PostgreSQL；保留 memory ID、操作语义、幂等收据、expected_revision、epoch、时间区间和删除作业接口。

**理由。** 存储后端变化不应让用户的“撤销”在云端变成另一种含义。先稳定接口与语义测试，再替换数据库适配。

**代价。** 两种后端的隔离级别、锁、全文检索和时间处理并非天然等价，必须运行同一组语义与故障测试；不能承诺复制 schema 即可迁移。

**重新评估条件。** 出现真实团队需求和部署预算后再启动，不以“未来可能需要”为由提前维护两套生产后端。

### ADR-09 采用开源组件，以固定版本证据决定范围

**选择。** 复用 DSH 接入与 UI；把 Mem0、Letta、Graphiti、Cognee、文件式记忆等作为对照、算法参考或独立适配候选，不同时堆叠为四份记忆权威。具体项目事实见[开源项目调研](research/projects.md)。

**理由。** 生命周期规则必须由一个系统解释；多套自动更新/删除策略叠加会增加不一致和评测混淆。

**许可处理。** 本地 DSH core、memory-lite 和根仓库文件声明 MIT，详见[代码审查](research/local-integration.md)。拟采用的每个外部版本分别记录源码 LICENSE、依赖许可、分发方式与 NOTICE；模型权重和托管 API 条款单独核对。调研时仓库证据不代表未来版本不变，也不构成法律保证。

## 6 差异验证与避免过早扩张

评测应同时包含传统长对话 QA 和完整生命周期任务。单次回答正确率不足以证明项目约束稳定：还要测修改后传播、旧来源重放、并发编辑、离线子任务、未来生效边界、备份恢复和外部副作用核实。

先比较以下可解释版本：近期上下文加文件/关键词、普通向量检索、结构化版本记忆、再加入上下文收据与动作检查的完整方案。逐项移除时间模型、关系补全、辅助模型或执行校验，观察哪些机制实际贡献收益。不要只和一个没有状态过滤的弱 grep 基线比较。

提前登记指标：误设约束、误删、过时信息误用、作用域误用、撤销后新动作误接受、恢复成功、任务完成质量、完整 token/费用、P50/P95 延迟、首次成功与手工纠错时间。模型、提示、数据与评价者版本固定，区分开发集调参和保留测试集。

已有论文、预印本和项目包含撤销与生命周期评测，因此预期新意应写成“待验证假设”：把稳定身份、双时间、删除屏障、上下文收据、任务租约及受控动作边界协同起来，是否在相同成本下改善真实多 agent 项目可靠性。若实验未证明，仍可作为工程产品贡献，但不能宣称首创机制或保证精度不下降。

暂缓通用图库、训练记忆策略、多地域多主、全量历史自动采集和每次检索都启动辅助 agent。只有某类失败在数据中反复出现，且新机制有对照收益时才扩大范围。

## 7 启动实施前的检查清单

- 确认目标平台、宿主版本、单用户/团队边界和可控工具范围。
- 固定本地/云端数据传输偏好，确认主任务模型也在数据流清单中。
- 选择少量真实但可授权使用的项目场景，准备脱敏和可公开的故障样本。
- 定义持久化确认、撤销接受边界、彻底删除范围和备份保留语义。
- 锁定依赖版本并记录源码与许可证据；保持最小依赖集合。
- 选定 P1–P3 的退出条件和试点用户任务，不提前承诺全部高级功能。

本包实际建立与运行的参考文件、检查命令及结果由交付清单统一列出。后续实施应在版本发布说明中持续区分“已实现且验证”“实验开关”“已设计未实现”和“尚未决定”，避免说明书中的拟议能力被误认为生产保证。
