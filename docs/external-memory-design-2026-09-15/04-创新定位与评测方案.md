# 外部项目记忆服务创新定位与评测方案

## 1 创新结论

本方案具备明确的工程实施价值，但不能保证学术新颖性。SQL、向量、标签、双时间、记忆增删改、权限、共享、人工编辑和撤销 guard 均存在直接先例。是否形成研究贡献，取决于具体新机制、与最接近工作的区别以及可复现的实验增量。

适合当前用户的定位是：**本地多 agent 工作站中的可编辑项目约束记忆服务，并配套端到端一致性和使用成本评测。** 第一阶段以可用、可解释、可恢复为交付目标；研究贡献作为独立假设检验，不把产品命名或组件组合写成新原理。

## 2 最接近工作如何限制主张

| 原本可能主张的创新 | 已有直接相关证据 | 本项目应如何定位 |
|---|---|---|
| 结构化记忆加标签，再交给模型增删改 | Mem0、A-MEM、SimpleMem | 复用或对照，不能主张首次 |
| 来源、版本、权限、迁移、订阅 | MemOS 正文已有相关设计 | 对照其具体接口与实现，不把概念当空白 |
| Markdown 加 SQL 加向量、人工编辑同步 | EverOS 当前实现说明；其他文件式记忆 | 作为用户体验与状态同步基线 |
| 项目记忆、时序事实和可解释证据 | LongMemory 当前说明 | 比较具体完整性、代价和接入范围 |
| 撤销后通过 guard 屏蔽旧记忆 | Revoked but Still Authoritative | 直接基线，不能称首次引入撤销检查 |
| 处理回写复活与多角色传播 | 上述撤销论文附录已有测试 | 扩展覆盖的具体场景必须说清楚 |
| 多 agent 授权撤销一致性 | CCS/RCC 与 VERA | 授权撤销与事实/约束变更分开比较 |
| 生命周期评测 | MELT、MemoryStackBench、相关新基准 | 扩展既有用例或适配器，避免重复发明基准 |

证据见 [项目调研](research/projects.md) 和 [论文调研](research/papers.md)。其中 2026 年 9 月 8 日的撤销研究在其测试设置中观察到被撤销内容仍被检索和采用，并提出检索 guard；该结果不能推广为所有版本、所有配置都失败。[论文](https://arxiv.org/abs/2609.08258)

VERA 研究授权委派图中的精确撤销目标，其正确性范围与运行时实际传播需要区分。这里可以借鉴契约与证据设计，但不能用一篇授权撤销论文直接证明本系统语义记忆正确。[VERA](https://arxiv.org/abs/2608.30091)

## 3 可检验的改进假设

### H1 条件和例外完整性的预算控制

候选机制：检索单元带必要依赖集合，组装器优先补全主体、否定、条件、例外和有效范围，再考虑增加新的背景条目；输出缺失依赖标记。索引仍用于找候选，完整性标记只证明已登记的依赖被处理，不证明自然语言抽取没有遗漏。

实验问题：在相同最终上下文预算下，与普通 top-k、父子块召回、图扩展及强重排相比，是否减少“只看到禁止、没看到例外”或相反的错误？是否增加检索成本和错误拒答？如果基础抽取经常漏依赖，机制不能靠后处理补救，需单独报告。

这是待确认的算法贡献方向。须继续按 constraint-aware retrieval、dependency-aware context selection、evidence completeness 等主题做专项查重，不能据本次调查宣称独创。

### H2 同一操作链中的约束变更和动作接受证据

候选机制：同一服务序号串联用户变更、SQL 版本、派生索引状态、上下文收据、任务 fence 和动作接受记录；把未来生效边界也纳入收据有效期。提供可重放轨迹，解释一个动作是在撤销提交前还是后被接受。

实验问题：相比仅提示、仅检索 guard、仅 TTL 缓存和已有授权撤销方法，该集成在索引延迟、agent 重启和未来规则切换下能否降低旧策略动作误接受，且不会大量中断无关任务？区分事实撤销、授权撤销与外部副作用。

分布式序列号、fencing、事务与回执都是成熟技术。本项目潜在贡献是特定工作站约束下的完整协议、实现和测量；是否具有论文增量仍需与上述先例逐项比较。

### H3 自主修改与用户打断的联合成本

候选机制：按操作风险、目标歧义和来源证据决定自动提交、保存假设或请求澄清。阈值按人工标签校准，而不是使用模型自报置信度直接设定固定概率门槛。

实验问题：在限制误删和误设约束的条件下，是否减少每百次记忆操作的用户确认次数、总时延和模型成本？对中文口语、否定、含糊指代与跨项目迁移分别报告。不能用“确认次数少”掩盖更多错误修改。

### H4 中文多 agent 工作站场景增量

候选贡献：在已有生命周期基准的接口上增加口头约束、条件例外、未来时间、直接人工编辑、并发工作树、旧 embedding 回调和进程中断。每个场景同时包含真值状态、允许范围、禁止输出、动作状态与来源证据。

成立条件：公开生成器、人工核验样例、基线适配器、固定版本、数据拆分、原始结果和成本，不仅提供一个排行榜数字。若与 MELT 或近期 LifecycleBench 已有用例重合，应提交扩展或复用其用例，并具体说明新增覆盖。

## 4 评测分层

### 第一层 确定性协议与存储

不调用大模型，先检查版本冲突、去重、时间区间、作用域、回滚、删除屏蔽、旧索引回调、策略 epoch 和 fence。使用固定事件轨迹和故障注入。当前交付中的参考验证属于这一层的有限子集；不等于生产协议经过形式化证明。

### 第二层 意图与记忆更新

输入原始对话，输出结构化变更；由人工真值判断操作、目标、范围、时间、否定、条件和来源是否正确。评分必须包括错误删除、错误覆盖与不应创建的约束，不能只看成功提取的条数。

### 第三层 检索与最终行为

先测候选召回和证据完整性，再测回答及真实模拟动作。检索到正确事实不等于模型采用正确；答案提及旧规则也不总是违规，需区分“解释历史”与“把旧规则当作当前要求”。

### 第四层 真实接入和易用性

在 DSH 主任务与子任务中验证身份传播、第一轮上下文、直接编辑、撤销通知、工具入口、任务重启和迁移。对普通用户测首次完成、纠错时间、误操作和理解程度。

## 5 数据集建议

最小自建集合为 12 类、每类 20 个独立情景，共 240 个情景；每个情景生成中文和英文实例。480 个语言实例不等于 480 个独立实验单位。训练/开发/测试按情景图分组，同一情景的翻译和改写必须放在同一分区。

| 类别 | 关键对照 |
|---|---|
| 明确要求与偏好 | 必须、最好、可以、可能 |
| 否定与引用 | 禁止、不再禁止、引用旧命令 |
| 指代与范围 | 那条、这个项目、本次任务、全局 |
| 条件与例外 | 生产/演示、一次性、授权前置 |
| 时间与纠错 | 未来生效、历史回顾、回溯修正 |
| 替换与撤销 | 解除要求不产生相反命令 |
| 人工编辑 | 文件/UI修改、旧提取器回写 |
| 并发更新 | 两个 agent 基于相同版本更新 |
| 检索与索引延迟 | 新记忆未索引、旧回调晚到 |
| 项目和权限 | 同词异项目、授权变更、委派范围 |
| 中断和恢复 | 提交前崩溃、响应丢失、任务租约失效 |
| 彻底删除 | 摘要依赖、旧备份恢复、历史查询 |

并发情景使用固定随机种子生成多个调度顺序；统计时按独立情景聚类，不把同一情景的几十次重试当作几十份独立证据。保留一批用户真实项目的去标识化且获授权案例作为独立外部测试；本次没有读取或导出真实用户对话。

## 6 公共基准怎么用

LoCoMo 与 LongMemEval 用于对话信息、更新、时间推理与缺证据回答；MemoryArena 与 LongMemEval-V2 用于跨会话任务经验；LOCOMO-CONV 用于隐含信息需求。它们的任务构成不同，不宜混成一个总分。[LongMemEval](https://arxiv.org/abs/2410.10813)、[MemoryArena](https://arxiv.org/abs/2602.16313)、[LongMemEval-V2](https://arxiv.org/abs/2605.12493)、[LOCOMO-CONV](https://arxiv.org/abs/2609.03467)

生命周期测试优先适配 MELT 与 MemoryStackBench，固定具体版本、场景集合和评分器，再补充本项目特有事件。基准存在不代表其所有评分已独立验证；抽样人工复核错误案例，避免只依赖模型评审。[MELT](https://github.com/shisa-ai/MELT)、[MemoryStackBench](https://github.com/aetna000/MemoryStackBench)

## 7 基线与消融

| 阶段 | 基线 | 比较目的 |
|---|---|---|
| 第一轮 | 最近上下文加人工维护 Markdown/关键词 | 检查复杂架构是否确有必要 |
| 第一轮 | 普通 SQL 过滤加全文/向量混合检索 | 隔离生命周期机制的增量 |
| 第一轮 | 当前 DSH memory-lite 固定版本 | 直接衡量对现有用户的收益 |
| 第一轮 | ReMe 的现有 DSH 插件与固定服务版本 | 检查能否直接适配，重点测批量保存窗口和子 agent 覆盖 |
| 第二轮 | Mem0、Graphiti、SimpleMem 的锁定版本 | 比较自动记忆提取与检索 |
| 第二轮 | EverOS、LongMemory、MemOS 的适用版本 | 比较文件编辑、项目治理、生命周期 |
| 专项 | 撤销论文 guard、MELT/相关适配器 | 比较失效与撤销行为 |

采用哪些基线应根据其许可、可运行性与客户端范围最终确定。不能让一个基线使用固定小预算、另一个使用大模型全文和额外重排，再把差异全部归因于架构。

消融依次移除：时间管理、结构化命题、条件依赖补全、执行入口校验、辅助重排、人工确认策略。每次只改变对应组件，保持模型、数据、预算和重试策略一致。记录无法保持一致的差异，而不是隐去。

## 8 指标定义

| 指标 | 定义与注意事项 |
|---|---|
| 变更精确率 | 自动提交且操作/对象/范围/时间均正确的数量 ÷ 自动提交数量 |
| 错误撤销率 | 被错误撤销的仍有效要求 ÷ 涉及撤销判断的要求数量 |
| 当前证据召回 | 需要的当前有效证据被召回比例；条件和例外单列 |
| 过时信息误用率 | 应使用新状态的任务中，把旧内容当当前依据的比例 |
| 撤销后误接受 | 撤销提交后仍被受控入口新接受的违规动作数；已派发动作另计 |
| 删除复活率 | 删除/撤销后重放来源、回写或恢复使内容重现的比例 |
| 范围隔离违规 | 不被授权的正文、来源、摘要或候选泄漏次数 |
| 无证据臆测率 | 应回答不足时仍编造事实的比例 |
| 总成本 | 记忆写入、embedding、重排、主模型、重试、重建的完整调用成本 |
| 时延 | 写入确认、提取完成、检索、变更可见、动作校验分别报告 P50/P95 |
| 用户负担 | 每百次修改的澄清数、完成时间、手工纠错数 |

分母为零时报告不适用，不显示 100%。按场景类型报告均值与置信区间，使用配对比较和按情景聚类的 bootstrap；先登记主指标与阈值，再运行测试集，避免看到结果后更换“最有利指标”。

## 9 易用性验收目标

在依赖已安装且本地模型可用的条件下，建议目标为首次关联项目并完成一条记忆的查看与修改不超过五分钟；这些前提必须在测试说明中列出，不能忽略安装/下载时间后宣传五分钟完整部署。

招募 5–8 名目标用户做形成性测试，先验证术语、撤销与彻底删除的区分、作用域选择和冲突提示。该样本用于发现问题，不能据此宣称普遍使用效果。后续扩大样本并记录设备与经验差异。

关键任务：设一条口头约束、建立本次例外、查来源、查看哪个任务用了该记忆、撤销、观察旧任务处理、从中断恢复。页面不要求用户理解 SQL、向量或 epoch。

## 10 成本模型与停止条件

设写入成本为 W，查询次数为 Q，单次检索与筛选成本为 R，主模型减少的重复上下文成本为 S，则净节省近似为 `Q × (S − R) − W`，再加上维护、缓存与失败成本。该式只是记账框架，必须使用实际输入输出 token 和所用服务价格，不能把所有 token 当同价。

若复杂检索在相同质量下不能优于关键词基线，应保持简单实现。若辅助模型减少主模型输入但增加总成本或时延，应按用户档位关闭。若新机制未显著改善既有最接近基线，报告工程集成结果和失败案例，不包装成研究突破。

## 11 当前交付实际验证范围

`validation/reference_model.py` 与 `validation/test_reference.py` 使用 SQLite 和确定性命令验证部分状态规则。实际数量、运行时和通过情况以 `validation/results.json` 为准。

没有在本次运行 LLM 记忆基准、安装上述所有项目、验证 embedding 召回、部署 HTTP/MCP 服务、实测云端扩容或证明专利/论文新颖性。原型通过不代表未实现的机制已获验证。完整产品的验收门槛以本文件和实施路线为准。
