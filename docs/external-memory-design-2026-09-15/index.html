外部项目记忆服务调研与设计总览

调研截止 2026 年 9 月 15 日。面向本地多 agent 工作站，后续扩展云端。

推荐方案

采用独立的项目记忆服务：SQL 管理有效记录、时间、版本和来源；全文与向量用于背景召回；适用约束确定性加载；宿主适配器绑定真实身份；统一写入接口处理人工编辑、撤销、索引更新和任务恢复。

先验证 ReMe、EverOS、LongMemory、MemOS 与现有 DSH memory-lite 的适用能力。满足要求时优先适配；缺少关键生命周期契约时再实现对应模块。不同对象可以有不同来源系统，但同一对象只能有一个权威写入点。

这次实际完成了什么

  • 45 项论文与预印本记录，含一项综述；其中 16 项核对关键正文，29 项核对摘要与元数据。
  • 产品架构、数据协议、使用与运维说明、创新评测方案、实施路线与决策记录，以及当前 DSH 的源码接入审查。
  • 11 个路径的 OpenAPI 草案、24 个数据结构、SQLite 核心骨架和输入样例。
  • 37 项有限参考模型检查通过，覆盖时间、版本、撤销、部分双连接交错和进程退出恢复。完整范围见验证报告。

三个判断

可行性： 核心依赖采用成熟存储和服务机制；参考模型验证了部分确定性规则。自然语言理解、完整集成、性能与模型收益仍需实施和实验。

易用性： 用户直接看“记住了什么、在哪里适用、什么时候生效、来自哪里”，通过普通编辑和撤销操作控制记忆。隐藏向量、ID 和版本等内部细节，保留高级审计入口。

创新性： 原构想的大部分机制已有直接先例，不能保证首次或论文新颖性。建议把新增贡献收窄为条件证据完整性、约束变更至动作接受的联合证据，以及本地中文多 agent 场景的可复现增量；每项都设对照和停止条件。

最重要的边界

1 设计结论

建议建设一个本地优先、可独立运行的项目记忆服务。SQL 保存带来源、有效时间与版本的记录；全文和向量索引负责召回；当前适用的约束通过确定性查询加载；统一服务负责人工编辑、并发写入、撤销传播与访问授权。DSH 是第一个适配目标，HTTP API 与 MCP 是兼容其他 agent 的入口。

实施前先对照现有组件，尤其 ReMe 已提供 DSH 插件，EverOS 与 LongMemory 也已覆盖大量原设想。下文是目标架构和自建缺口模块的参考契约，不意味着需要重写所有存储与检索能力。若现有后端满足不变量，优先适配；若只提供背景记忆，则可由它管理背景，本服务独立管理用户约束，按对象明确各自权威来源，禁止同一对象多头写入。

本包交付的是可实施的设计、接口草案、数据库骨架和有限范围的参考验证，不是已经安装运行的完整产品。自然语言理解、任意约束的遵守率、性能收益及研究新颖性需要后续实验。所有性能数字均是待测目标或容量估算，不能作为现有系统成绩。

当前设想应保留的部分：外部持久化、结构化记忆、语义检索、用户可编辑、按任务组织上下文。需要改变的部分：不依赖隐式思维链；不让最新时间戳自动决定覆盖；不把标签当授权；不把共享数据库当作跨 agent 一致性保证。

3 第一版边界

默认场景为一个用户、一个本地服务、多个项目和最多十余个并发 agent；这些是设计假设，不是已测容量。服务由宿主机运行，数据库位于持久目录，容器通过认证连接访问。不同机器的客户端不直接打开共享 SQLite 文件。

第一版包括：事件接收、记忆变更、项目约束、时间语义、全文检索、可插拔向量检索、人工编辑、撤销、上下文收据、任务检查点、MCP 适配、状态与恢复页面。

延后：跨地域多主写入、通用自动知识图谱、强化学习训练写入策略、任意自然语言规则的完全形式化、无条件恢复全部外部操作、所有历史全文常驻。原型先做清楚的单写入点，再根据负载迁移数据库。

5 记忆内容和存储模型

5.1 三种内容层

原始证据。 用户消息、人工编辑、工具观察、明确决策和工作检查点。保存最小必要上下文与来源引用。模型隐藏推理不在采集范围内。工具声称成功与环境实际状态要区分，重要结果保留可核验引用。

结构化记忆。 一条可独立理解的陈述：主体、谓词、内容、否定、范围、条件、例外、来源与时间。类型使用受控枚举：constraint、goal、preference、fact、decision、procedure、work_state、hypothesis。类型和操作分开；“删除”是操作，不是永久内容类别。

派生视图。 短摘要、标签、全文索引、向量、Markdown/JSON 导出、界面搜索视图。这些内容可重建，不能单独决定当前有效版本。

5.3 时间模型

记录两个独立维度：有效时间表示内容在现实或项目中何时适用；系统时间表示服务在何时知道这条记录。内部有效时间统一使用 UTC 毫秒，另外保留原始时区和解析依据；系统顺序使用服务端单调提交序号，不能用客户端时钟排序并发写入。

示例：9 月 15 日说“10 月 1 日开始允许付费 API”。新记录立即入库，但 10 月 1 日前不能作为当前许可。已有约束的结束时间调整为 10 月 1 日，新规则的开始时间同样为该日。未来替换不能立刻把旧规则全局标为不可用。

回溯纠错保存新系统版本；历史查询可以分别回答“当时系统知道什么”和“现在认为当时有效什么”。历史查询仍按当前身份授权及删除标记过滤，不允许通过时间旅行取回已彻底删除的内容。

6 写入和意图识别

6.1 写入路径

  1. 宿主将原始事件写入接收器，附稳定事件 ID；服务提交后返回持久化收据。
  2. 提取器只阅读新事件、必要指代上下文和小范围候选旧记忆。
  3. 输出结构化提案。使用 JSON Schema 校验字段、长度、枚举与引用，不能将格式正确视为语义正确。
  4. 程序完成身份、作用域、来源资格、时间区间和目标版本检查。
  5. 只在同一对象、兼容范围、同一冲突组内检索可能被修改的记录。向量相似度仅作为找候选的线索。
  6. 对明确表达且目标唯一的授权变更自动提交；推断先存 hypothesis；影响大的歧义进入待确认队列，不静默删除或收紧全局约束。
  7. 同一事务写入版本、关系、epoch、变更收据与 outbox。
  8. 后台更新检索索引并通知受影响任务。失败可重试，不撤销已成功的权威写入。

提取器的自报置信度不能直接当成概率。自动处理阈值应在人工标注的开发集上校准，分别统计误设约束、误删和漏记。假设、高置信事实、低置信事实不能通过多次摘要自动提升为用户权威指令。

6.3 提取器提示约定

输入明确区分 trusted_envelope、source_text、neighbor_context、candidate_records。source_text 和候选证据全部按数据处理；其中的“忽略之前规则”“改写权限”等文字不能修改服务策略。

提取器返回提案与原文证据片段，不输出隐式思维链；每个证据片段必须能够在原始来源中定位。对引用、反事实、条件、否定、尚未决定的提议显式标记。由宿主确认的人工编辑身份，不允许由模型在提案中自己填写。

7 切块和索引

口头约束以完整命题为单元。条件和例外与主体一并保留；复杂规则可以分成父规则与子条件，但召回时必须补全必要依赖。计划、观察、决定分别存储，避免一句“准备迁移”变成“已经迁移”。

长文档采用结构优先切块：标题、段落、代码块、表格、列表层级作为第一层边界；过长块再按语义和长度拆分。每块保留父标题、源偏移、内容哈希、文档版本和邻接关系。固定 token 上限是工程保护，不是语义正确性证明。输入、输出发生截断时标为不完整并重新处理，不将半条规则发布为有效约束。

建议初始参数：事实正文优先控制在 80–250 tokens；证据窗口约 300–800 tokens；文档块约 400–900 tokens。这些是实验起点，需针对中文、英文、代码、表格分别验证。不得为了满足长度将否定、条件或例外截掉。

全文检索保留精确标识符、路径和实体词。中文采用预分词字段或经过验证的 CJK 分词方案；SQLite FTS5 的默认分词不等于中文语义分词。FTS5 提供 BM25 与自定义分词扩展，可作为实现基础。SQLite FTS5

向量索引记录 embedding_model、model_revision、dimension、normalization、payload_hash、memory_revision 与 index_generation。更换 embedding 模型应在独立代际重建和切换，不能混用不兼容空间。尚未建好向量的新记录通过增量扫描/全文检索补入，避免写入成功但立即搜索不到。

8 检索和上下文组装

8.1 必需约束路径

服务依据可信身份、当前项目/分支/任务、动作类型和有效时间，直接查询约束、明确例外和未决冲突。窄范围规则不会自动覆盖广范围规则；覆盖或例外必须有明确关系及相应修改权限。

可机器执行的约束进入动作网关；自然语言约束作为完整内容注入当前请求。必须区分三种保障等级：

  1. 机器强制：如允许写入的目录、允许调用的工具、预算边界，能由可信网关判定。
  2. 上下文遵守：如视觉风格、叙事语气，依赖模型理解与结果检查，不能给出绝对保证。
  3. 尚未解析：条件或指代不清，影响相关动作时提示处理。

必需约束超出预算时，优先缩小任务范围、拆分动作或构建无损的规则清单；不允许静默把禁止项交给向量 top-k 丢弃。

8.2 背景检索路径

解析当前任务为若干信息需求，例如“接口定义”“以前的失败”“用户偏好”。在授权范围内并行执行精确 ID、全文和向量召回，使用排名融合而非未经校准的异构分数直接相加。建议以 RRF 作为简单起点，参数纳入消融实验。

随后回查 SQL 的当前版本、有效区间、来源和删除状态；补全条件、例外和父块证据。重要条件缺失的候选不得独立进入最终上下文。对需要语义裁决的少量候选调用重排模型；标签和时间戳由程序先过滤，避免让辅助模型反复通读整个库。

过滤与 ANN 相互作用可能造成候选不足；不能先从全库取少量结果再全部过滤后宣布无记忆。应在允许范围内检索，必要时扩大候选或对小集合进行精确搜索。pgvector 官方明确说明了近似索引过滤后结果不足以及迭代扫描的处理方式。pgvector

8.3 上下文预算

为当前请求保留最近对话、当前目标、未解决事项和任务状态。其余预算由“适用约束、必要证据、相关背景”分配。不要把上下文压缩等同于只保留最后一句对话。每次组装返回所用 ID、版本、来源、选入原因与未覆盖的信息需求；缺少证据时允许返回不足，而不补造记忆。

初始背景召回候选数可设全文 20、向量 20、增量 10，融合后语义重排不超过 12，最终按预算选择。这些是配置默认候选，不是性能保证。用户可以选择更快、均衡、更完整三档；后台仍展示实际成本。

9 约束修改 撤销和删除

替换新增记录并明确关联被替代记录，在同一事务调整有效区间。撤销结束原要求的适用期，不产生相反命令。纠错记录系统认知变化，保留必要的时间语义。归档降低普通记忆的默认检索优先级；有效约束不能因归档失去约束力。普通文字整理 AMEND 只允许不改变断言语义和时间的修订；新的现实要求使用 REPLACE，纠正过去记录使用 CORRECT。参考模型只实现显式 CORRECT，不实现完整未来 REPLACE。

旧来源重放必须经过事件去重、来源处理位置及目标版本检查。撤销关系和人工修订版本阻止旧提取结果悄悄覆盖当前状态；用户真正重新启用旧规则时必须形成新的明确事件。

彻底删除先在权威库写入不可读取标记并提升相关 epoch，所有普通及历史读取立即屏蔽。之后执行正文、证据载荷、派生摘要、FTS、向量、缓存和受控导出副本的清理。审计记录仅保留无正文的操作元数据。无法控制的用户下载文件或外部 provider 副本需在作业范围中明确列出。

SQLite 删除行不自动等于磁盘残留全部不可恢复。实施时应处理数据库/WAL/FTS 的清理策略、备份期限和恢复过滤；需要更强删除能力的部署可采用独立加密载荷与密钥生命周期，仍需证明副本和密钥备份范围。界面分开显示“停止使用”“在线副本清理”“备份到期”，不得提前宣布所有副本已永久清除。

10 多 agent 和跨容器协议

10.1 身份与作用域

身份来自宿主适配器或连接凭据。模型提供的 project_id 只是请求目标，必须与授权交集核对。global 表示当前租户/用户的全局，绝不表示所有用户共享。不同 agent 的标签偏好用于相关性路由，ACL 用于授权，两者独立。

HTTP 服务按身份发放作用域限定的凭据。MCP 是工具访问协议，并不自动提供项目级记忆权限；HTTP 模式应按所选版本实现相应授权要求，本地 stdio 由宿主安全提供连接凭据。MCP 授权

10.2 乐观并发与版本

所有定向修改提交 expected_revision；冲突返回 409，并提供允许读取的新版本及差异。幂等键按身份隔离，复用同一键但改变请求内容报冲突。单服务事务提交提供顺序；普通数据、约束和 ACL 使用不同 epoch，避免一条无关笔记使所有 agent 重启。

10.3 上下文收据和动作校验

收据绑定身份、任务、所读作用域 epoch、记忆版本、快照序号和到期时间。到期时间还必须早于下一项相关规则开始/结束生效的时间；否则未来规则在时间到达后、没有新写入时仍可能被旧收据绕过。

每个受控动作在服务端入口重新检查 epoch、授权、时间边界和任务租约。策略变更与动作接受在同一顺序域中协调。只在客户端先查一次再异步执行，不能消除检查后规则变化的竞争窗口。

可承诺的撤销边界：撤销提交以后，受控网关不再接受依赖旧策略的全新动作；已被接受或已经发往外部的动作按运行状态尽力取消或补偿，不宣称可以时间倒流。纯 MCP 只读接入的 agent 只能获得记忆更新，不能宣称已经覆盖所有外部副作用。

10.4 子 agent 和任务租约

子 agent 在创建时继承经过收窄的身份、项目范围和当前约束引用，不复制可无限期使用的旧授权。任务分配使用带到期时间和单调 fence 的租约；旧执行者恢复后，其过期 fence 被存储和动作入口拒绝。无法拦截的本地文件操作仍需宿主集成才能达到该约束。

普通背景可使用任务快照提高可复现性；当前授权和当前适用约束始终再次核对。跨任务恢复读取检查点、当前规则和待完成工具操作，不把旧计划直接当作已完成事实。

11 持久化和故障恢复

SQLite 使用本地持久盘、事务、WAL 与明确的同步配置。高可靠配置采用 synchronous=FULL；持久性仍依赖操作系统和存储设备正确实现同步。WAL 有单写者特性，不适合作为跨机器共享文件接口。SQLite WAL、同步配置

数据库提交和 outbox 投递采用至少一次处理与幂等消费。系统不宣称网络与外部工具端到端天然“恰好一次”。进程崩溃后从已提交位置恢复；未确认提交的请求使用原幂等键重试。

原始事件确认与提取完成分开显示。关键口头约束应在当前任务继续相关动作之前完成解析与提交；不能仅显示“消息已保存”就让动作沿用旧规则。普通背景可异步处理。

备份通过数据库支持的一致性方式产生，不直接复制忙碌数据库的某一个文件。恢复时先校验完整性、重放删除清单，再开放查询并重建派生索引。SQLite Backup API

12 易用性设计

主要界面只显示用户能理解的字段：记住了什么、在哪里适用、什么时候生效、来源、当前状态。ID、epoch、向量模型等进入高级详情。

导航包括：当前项目记忆、约束与例外、待确认、最近变更、任务正在使用的记忆、删除进度、服务状态。默认不要求用户写标签或 SQL；项目和来源自动填充，用户可以纠正。

每条记忆提供编辑、停止使用、设为长期、查看来源和查看影响。彻底删除使用独立操作，并明确列出范围。普通可逆编辑直接保存，提供撤销；只有指代不明或有实质冲突时才要求用户选择目标。

结果解释应短而具体，例如“此任务采用你的项目约束，来源于 9 月 15 日的消息；演示例外只适用于另一个任务”。不要向普通用户展示向量分数作为正确性证明。

14 估算和服务目标

以下为设计起点：十万条有效记录、平均正文和元数据 2 KB 时约 200 MB，不含索引、历史和证据。若每条使用 1024 维 float32 向量，原始向量约 409.6 MB；双代际重建约翻倍，ANN 开销需实测。原始聊天与工具输出往往比结构化记录更大，必须配置保留策略。

建议测量目标：不含模型调用的当前约束查询 P95 小于 100 ms；普通本地检索 P95 小于 300 ms；界面变更通知正常情况下小于 1 秒；持久化确认写入在宿主进程崩溃后的逻辑丢失数为零。均须在声明 CPU、存储、数据规模和并发数的环境中验证，不能直接作为承诺。

对于机器可判定约束，验收要求协议测试中零旧版本动作被误接受；对于自然语言约束，分别测识别与最终遵守率。总体成本按写入、提取、更新、embedding、重排、主模型输入输出、重试与索引重建累计。

15 仍需验证的风险

中文隐含意图、代词范围与条件抽取仍可能出错；人工确认太多会破坏易用性；人工确认太少会扩大误写。动作网关覆盖度决定强制能力，纯文本上下文不能替代它。标签过细可能导致漏召回，关联补全过多又会吃掉预算。更复杂的图检索与辅助 agent 需要用真实任务验证收益后再启用。

设计以明确不变量和可复现评测降低这些风险；没有从“外置存储”自动推出“完全正确、绝不遗忘或一定省 token”的推论。

外部项目记忆服务数据与接口协议

1 协议范围

本文为 0.1 版接口设计。spec/openapi.json 是机器可读的核心 HTTP 契约；spec/schema.sql 是 SQLite 核心存储骨架；spec/examples.json 包含输入样例。它们没有启动实际 HTTP/MCP 服务。身份提供方、模型提供方、索引工作器和真实工具网关需要按本文实现。

HTTP 与 MCP 共用同一业务层，不能各自维护一套状态。所有会改变有效记忆的操作均经过来源、身份、范围、版本和幂等校验。默认拒绝未知字段；协议升级需增加 schema_version。JSON 格式可校验不代表事实正确。

2 可信请求信息

连接层确定 actor_id、tenant_id、可访问 scope、凭据版本。请求体不能自行提升身份。宿主适配器可以将真实用户消息登记为 user_message；模型直接调用 memory.propose 只能登记为 agent_proposal。两者不能通过一个 source_type 字符串互相冒充。

Idempotency-Key 用于写入重试。服务将规范化请求的摘要与该身份、幂等键一起保存。相同内容返回同一结果；不同内容返回 IDEMPOTENCY_CONFLICT。认证与授权必须在返回缓存结果前执行。

时间传输统一为 RFC 3339 UTC 字符串，SQL 中统一为 UTC 毫秒；系统提交顺序使用服务端 commit_seq。输入时区、相对时间解析上下文存于来源元数据。版本与时间不得由客户端自己宣称已获批准。

3 记忆对象

一个读取响应的概念示例：

{
  "memory_id": "mem_api_budget",
  "revision": 3,
  "scope_id": "project_alpha",
  "kind": "constraint",
  "subject": "external_api",
  "predicate": "paid_usage",
  "content": "本项目不得调用付费 API；经过明确授权的演示任务可例外。",
  "assertion_status": "accepted",
  "valid_from": "2026-09-15T00:00:00Z",
  "valid_to": null,
  "conditions": {"environment": ["production", "development", "demo"]},
  "source": {"event_id": "evt_41", "source_type": "user_message"},
  "evidence_refs": [{"event_id": "evt_41", "quote": "本项目不得调用付费 API；经过明确授权的演示任务可例外。"}],
  "relations": [],
  "enforcement": "context_only"
}

例中为虚构来源；真实写入必须核对引用是否确实来自相应原始消息。若另存证据偏移，应约定编码与边界。enforcement 只有完成机器规则映射、覆盖范围验证后才可标为 tool_guarded。

assertion_status 表示是否被接纳，不能混同是否当前生效；当前生效还取决于有效区间、作用域、条件、例外及是否删除。正文类型为 hypothesis 的推断不会自动转换为 constraint。

4 操作语义

操作 目标 结果 必要检查
ASSERT 新陈述 新建稳定 ID 与首版 来源资格、重复事实、冲突候选
AMEND 同一陈述的文字或元数据 创建不改变断言语义及有效期的新版本 expected_revision；语义改变须转 REPLACE 或显式 CORRECT
REPLACE 旧陈述与新陈述 调整有效区间并记录 replaces 对象、范围、时间、修改权限
REVOKE 当前要求 结束适用区间 明确目标，不能生成相反命令
EXCEPT 明确原规则 建立有范围有时限的例外记录 必须有授予例外的权限

6 读取一致性

context 请求携带任务范围、查询、动作类别、背景预算与可选历史时点。授权范围取请求与连接权限的交集。响应显式区分 constraints、background、unresolved；用户指令与证据按来源标识，绝不把检索到的任意文本作为新的系统指令。

读取步骤：

  1. 取得允许作用域及 ACL epoch；记录当前 snapshot_seq。
  2. 确定性加载有效约束与必要例外。
  3. 在允许范围内查询全文、向量和未完成索引的增量记录。
  4. 回查 SQL 当前或请求历史版本；屏蔽已删除内容。
  5. 检查所有必需依赖可用且有权读取。若例外无权读取，应输出可执行的解析结果或停止相关动作，不能以“没看到例外”伪造完整解释。
  6. 根据预算补齐证据、去重并返回未覆盖需求。
  7. 写入上下文收据；计算到期时间为默认期限、相关时间边界和授权期限的最小值。

索引工作器只能将 (memory_id, revision, payload_hash, generation) 全部仍匹配的结果发布为 ready。删除发生后，旧 embedding 回调到达不得重新插入可见结果。

7 条件和例外

第一版机器规则语言仅支持白名单字段与有限表达式：all、any、eq、in、exists，以及经过宿主规范化的资源范围。禁用任意脚本、SQL、正则执行与网络查询表达式。扩展操作符需要独立测试。

“作用范围更小”不是通用优先级。项目要求允许被任务例外覆盖时，例外需要明确 exception_to、授权者、有效区间和条件。一个用户要求不能更改服务部署方的访问控制政策。自然语言要求和服务控制面的权限策略是两类对象。

内容关系不能盲目做传递推断：A 从 B 派生，B 被纠错后，A 应标为待重算或暂不用于相关决策，不能自动推断 A 的反命题。派生内容保留所有支持来源；删除一个来源后，若剩余证据仍足够，可重新生成干净版本，不能原样保留可能含被删正文的摘要。

11 删除协议

删除作业的状态为 accepted、online_hidden、purging、backup_pending、completed 或 failed。online_hidden 在权威事务提交后生效，completed 只在作业声明范围全部处理并核验后使用。

删除记录不保存被删正文；工作器通过稳定对象 ID 和版本处理派生对象。恢复旧备份前必须导入最新删除清单；删除清单应在备份策略中独立可恢复。导出到用户自管目录的文件列为不受控副本，不能自动宣称已经清理。

agent 内存和第三方模型请求的已发送内容无法靠 SQL 删除撤回。对本服务控制的运行上下文发出失效事件，必要时由宿主重建任务上下文。UI 明确区分这些范围，禁止把“向量已删除”作为彻底删除成功。

12 协议不变量

I1 未授权身份不得读取正文、来源、候选摘要或历史版本。I2 新写入记录只有提交后才能获得持久化确认。I3 同一幂等键不会产生两次不同修改。I4 并发旧版本不能静默覆盖。I5 索引结果必须回查权威版本。I6 未来替换不会提前解除当前约束。I7 删除标记覆盖历史查询与旧索引回调。I8 有效约束不因热度衰减消失。I9 旧上下文和过期租约不能通过受控动作入口。I10 对外副作用只能按真实接入覆盖范围承诺顺序与恢复。

参考验证脚本验证其中一部分 SQL 与程序状态行为；完整产品验收还需真实客户端、模型、并发进程、网关和存储故障测试。详见评测文件和验证结果。

1 这个服务帮助你做什么

服务保存项目中的明确要求、决定、偏好和可核验的工作状态，在新任务开始时提供当前适用的内容。你可以看到它记住了什么、来自哪里、何时生效，以及哪些任务正在使用。

“请用中文回答”属于偏好，“本项目不调用付费 API”属于约束，“尝试过方案 A，测试失败”属于有来源的工作记录。系统应把它们分开，避免把讨论中的设想变成强制要求，或把计划当成完成结果。

你通常只需说清内容和适用项目。标签、索引和存储版本由服务管理，高级详情提供给需要排查的人。

2 首次使用：关联项目和数据偏好

2.1 关联当前项目

拟议首次使用页显示当前账户、服务位置和宿主识别出的项目。确认项目名称后，服务分配稳定的项目身份；日后目录移动或容器路径改变，应关联同一个项目，而不是再建一份记忆。

示例：宿主路径为 H:/Shop，容器路径为 /workspace/shop。只要它们在可信项目配置中指向同一个项目，就能共享项目记忆。服务不会仅因文件夹都叫 shop 就自动合并。

已有项目可通过“关联现有项目”选择；复制代码创建独立项目时，默认只复制明确选择的记忆，不自动继承全部历史。分支规则和一次性任务例外会单独显示适用范围。

“我的全局记忆”表示当前用户在其获准项目中的通用偏好，不表示其他用户或所有 agent 都可以读。角色和组织授权仍然适用。

2.2 选择数据传输偏好

记忆存在哪里与模型在哪里处理是两件事。即使数据库在本机，云端提取器、向量模型、重排模型或主任务模型仍可能收到内容。拟议设置页分别列出以下路径：

偏好 使用效果
全程本地 原文、记忆和查询只交给已配置的本地服务与本地模型；缺少本地模型时保留手工编辑和关键词检索

默认采用本地优先。已经配置云端主模型时，界面必须说明“送入任务上下文的记忆将随请求发送到该模型”。仅关闭云端 embedding 不等于所有内容都留在本地。

偏好变更会约束后续发送，不能收回已经发送给其他服务的数据。无法满足当前传输偏好时，系统应停止相应处理并说明原因，不能自动换成另一个云端供应商。

2.3 完成第一次验证

用一条非敏感、容易辨认的要求开始，例如“本测试项目的文档采用中文”。确认页面出现该要求、来源和范围；新建一个同项目任务，检查“本任务正在使用”中是否出现它。随后撤销该要求，再创建任务，确认它不再作为当前约束出现。

这一流程验证最基本的保存、跨任务读取和撤销；不能证明全部语义理解与外部动作限制都正确。

4 怎样口头新增和修改要求

4.1 明确新增

你说：“这个项目的接口字段统一使用 snake_case。”

拟议系统保存为项目约束，并简短回显：“已记住：本项目接口字段使用 snake_case。”不要求你填写类型或标签。若“这个项目”已经由任务身份确定，无需重复询问。

你说：“也许应该改成 camelCase。”

它应进入讨论或假设，不能直接替换已有要求。待你明确决定后，再形成新的变更。

4.2 条件和一次性例外

你说：“生产环境禁止付费 API；这次演示允许用一次。”

页面应显示一条生产要求和一条指向它的任务例外。例外的任务范围、截止条件必须可见；下一个生产任务不能继承演示许可。若“一次”无法对应明确调用或任务边界，系统在相关动作前用具体候选澄清。

条件属于要求的一部分。检索到“可以使用”时必须一并显示“仅此演示任务”，不能把前后句拆开导致许可扩大。

4.3 未来生效

你说：“10 月 1 日起允许付费 API。”

界面用当前设置的时区展示完整生效日期，保留原始表达。生效前旧要求仍有效；到达时间边界后，新任务和新动作使用新要求。依赖旧要求的任务需刷新，不能因为没有新增消息就一直沿用旧许可。

“月底”“明年”“发布以后”需要明确的时间或事件依据。依据不清且会改变当前动作时进入待确认；普通背景可以继续保存，相关动作等待规则明确。

5 人工编辑、冲突和防止旧内容复活

在记录上选择“编辑”，修改内容、范围、条件或生效日期后保存。系统会记录编辑者和新版本，并展示受影响任务；常规编辑无需让用户理解版本号。

如果你打开编辑框后另一个 agent 已修改同一记录，系统不能覆盖对方的新内容。拟议冲突页并列显示“你打开时”“当前内容”“你的修改”，提供重新编辑或明确合并。未获准读取的修改不能通过差异页泄漏。

撤销编辑也会生成新变更。若期间已有其他变更，“撤销”需要重新核对当前版本，不能盲目回退整份数据库。

旧对话、旧摘要或旧备份可能包含已撤销要求。导入与重新提取必须遵守现有撤销和删除记录；只因再次看到相同旧文字，不会重新启用它。你明确说“恢复之前那条要求”时，系统可以创建新的启用事件并显示来源。

Markdown 和 JSON 可以导出、离线编辑后导入，但它们是编辑交换文件。文件变更先生成可检查的差异和版本化变更，不能让数据库和文件长期同时成为可独立覆盖的权威来源。

6 agent 可以读哪些内容

任务页面显示“可读取范围”，例如当前用户的全局偏好、当前项目共享接口与后端记录。这里的“全局”仍受任务授权约束；它不会因模型填写 global 标签而自动开放。

前端/后端等标签帮助检索相关内容，授权由可信宿主与服务端策略决定。协作任务需要额外资料时，可以提交具体请求，说明需要什么以及用于什么工作；是否开放由已有规则或有权限的用户决定，不靠另一个模型自由裁决。

子任务默认继承经收窄的范围。父任务结束、授权撤销或租约到期后，子任务需要重新校验，不能继续使用复制来的长期凭证。

“任务正在使用”区分三种情况：已准备上下文、已交给模型、等待刷新。检索到内容不等于模型实际看过；已交给模型也不等于它遵守了要求。可由工具入口强制执行的限制显示为“操作受控”，风格等自然语言要求显示为“依赖模型与结果检查”。

7 中断后如何继续任务

恢复页面展示最近已确认保存的位置、目标、当前要求、已验证结果、待办与需要核实的动作。你选择继续后，宿主先更新权限和当前约束，再恢复工作。

以下状态必须分开：

  1. 计划中：agent 打算执行，还没有开始。
  2. 已开始：动作已发出，但尚无可靠完成证据。
  3. 已确认完成：有工具结果或环境检查作为证据。
  4. 结果待核实：程序中断，外部操作可能已发生。

例如部署请求发出后程序崩溃，恢复不能因为缺少成功日志就再次部署。应先查询部署状态；无法自动核实的操作明确列出，再决定后续处理。文件写入也应检查实际文件与预期结果。

服务只能恢复已确认持久化的事件。尚未发送或尚未提交的最后一段文字不能宣称已保存。恢复后的旧进程若迟到提交，服务应拒绝它过期的任务身份，防止两个执行者同时接管。

9 备份、恢复与删除进度

9.1 备份

拟议备份包包含一致性的权威数据库、必要载荷、版本和迁移信息；索引可以重建，不要求每次完整复制。设置页展示保留周期、上次成功备份和恢复验证日期。

运行中的数据库应通过受支持的一致性备份接口处理。不要直接复制其中一个正在变化的数据库文件并把它称为完整备份；相关日志和载荷可能尚未一致。

9.2 恢复

恢复在隔离位置进行：校验备份、匹配版本、取得不早于删除请求的最新删除清单、应用删除与撤销信息、核验引用，再开放查询。已删除内容在恢复过程中也不能短暂暴露给模型。

如果只能找到很旧的备份，且无法取得最新删除清单，恢复状态应显示“无法确认删除记录完整”。服务不得自动向 agent 开放这份数据；应补齐清单或明确采用仅恢复可验证项目的流程。

恢复也不能覆盖备份产生以后仍存在的有效新事件。导入器按事件与版本去重，保留后续人工修改和撤销关系；“恢复旧版本”不是无条件替换当前整个记忆库。

9.3 彻底删除

拟议删除页分三层报告：

  • 停止使用：当前、历史和模型检索已经隐藏目标内容。
  • 在线副本清理：服务控制的正文、原始证据、派生摘要、全文/向量索引、缓存等已处理。
  • 备份处理：旧备份已清除，或会在显示的保留期限结束后失效；恢复流程持续应用删除清单。

删除清单保留执行恢复过滤所需的不透明标识、序号和状态，不保存已删除正文。它也必须受保护和备份，避免删除记录本身丢失造成复活。

用户下载到其他位置的导出文件、其他模型供应商保存的内容，以及宿主尚无删除接口的原始会话日志，都不能直接纳入本服务的完成保证。当前 DSH 原日志采用受版本管理的追加式记录；未来适配器若不能清理某类副本，页面必须逐项显示“尚未清理/不在控制范围”，不能靠删除记忆条目就宣布全部永久删除。

3 可检验的改进假设

H1 条件和例外完整性的预算控制

候选机制：检索单元带必要依赖集合，组装器优先补全主体、否定、条件、例外和有效范围，再考虑增加新的背景条目；输出缺失依赖标记。索引仍用于找候选，完整性标记只证明已登记的依赖被处理，不证明自然语言抽取没有遗漏。

实验问题：在相同最终上下文预算下，与普通 top-k、父子块召回、图扩展及强重排相比，是否减少“只看到禁止、没看到例外”或相反的错误？是否增加检索成本和错误拒答？如果基础抽取经常漏依赖，机制不能靠后处理补救，需单独报告。

这是待确认的算法贡献方向。须继续按 constraint-aware retrieval、dependency-aware context selection、evidence completeness 等主题做专项查重，不能据本次调查宣称独创。

H2 同一操作链中的约束变更和动作接受证据

候选机制：同一服务序号串联用户变更、SQL 版本、派生索引状态、上下文收据、任务 fence 和动作接受记录；把未来生效边界也纳入收据有效期。提供可重放轨迹，解释一个动作是在撤销提交前还是后被接受。

实验问题：相比仅提示、仅检索 guard、仅 TTL 缓存和已有授权撤销方法，该集成在索引延迟、agent 重启和未来规则切换下能否降低旧策略动作误接受，且不会大量中断无关任务？区分事实撤销、授权撤销与外部副作用。

分布式序列号、fencing、事务与回执都是成熟技术。本项目潜在贡献是特定工作站约束下的完整协议、实现和测量；是否具有论文增量仍需与上述先例逐项比较。

H3 自主修改与用户打断的联合成本

候选机制：按操作风险、目标歧义和来源证据决定自动提交、保存假设或请求澄清。阈值按人工标签校准，而不是使用模型自报置信度直接设定固定概率门槛。

实验问题：在限制误删和误设约束的条件下，是否减少每百次记忆操作的用户确认次数、总时延和模型成本？对中文口语、否定、含糊指代与跨项目迁移分别报告。不能用“确认次数少”掩盖更多错误修改。

H4 中文多 agent 工作站场景增量

候选贡献：在已有生命周期基准的接口上增加口头约束、条件例外、未来时间、直接人工编辑、并发工作树、旧 embedding 回调和进程中断。每个场景同时包含真值状态、允许范围、禁止输出、动作状态与来源证据。

成立条件：公开生成器、人工核验样例、基线适配器、固定版本、数据拆分、原始结果和成本，不仅提供一个排行榜数字。若与 MELT 或近期 LifecycleBench 已有用例重合，应提交扩展或复用其用例，并具体说明新增覆盖。

4 评测分层

第一层 确定性协议与存储

不调用大模型，先检查版本冲突、去重、时间区间、作用域、回滚、删除屏蔽、旧索引回调、策略 epoch 和 fence。使用固定事件轨迹和故障注入。当前交付中的参考验证属于这一层的有限子集；不等于生产协议经过形式化证明。

第二层 意图与记忆更新

输入原始对话，输出结构化变更；由人工真值判断操作、目标、范围、时间、否定、条件和来源是否正确。评分必须包括错误删除、错误覆盖与不应创建的约束，不能只看成功提取的条数。

第三层 检索与最终行为

先测候选召回和证据完整性，再测回答及真实模拟动作。检索到正确事实不等于模型采用正确；答案提及旧规则也不总是违规，需区分“解释历史”与“把旧规则当作当前要求”。

第四层 真实接入和易用性

在 DSH 主任务与子任务中验证身份传播、第一轮上下文、直接编辑、撤销通知、工具入口、任务重启和迁移。对普通用户测首次完成、纠错时间、误操作和理解程度。

9 易用性验收目标

关键任务：设一条口头约束、建立本次例外、查来源、查看哪个任务用了该记忆、撤销、观察旧任务处理、从中断恢复。页面不要求用户理解 SQL、向量或 epoch。

10 成本模型与停止条件

设写入成本为 W，查询次数为 Q，单次检索与筛选成本为 R，主模型减少的重复上下文成本为 S，则净节省近似为 Q × (S − R) − W，再加上维护、缓存与失败成本。该式只是记账框架，必须使用实际输入输出 token 和所用服务价格，不能把所有 token 当同价。

若复杂检索在相同质量下不能优于关键词基线，应保持简单实现。若辅助模型减少主模型输入但增加总成本或时延，应按用户档位关闭。若新机制未显著改善既有最接近基线，报告工程集成结果和失败案例，不包装成研究突破。

实施主线是先把变更正确地保存、检索与撤销，再增加模型自动整理和语义召回。第一版服务面向单用户、本机持久存储、多个项目和少量并发 agent；所有写入进入同一个权威服务。设计详见产品与架构，操作语义详见使用与运维说明。

已有研究和项目涉及版本、时效、撤销及记忆生命周期，不能把这些概念宣称为独创。研究贡献应落到可复现的机制组合、明确边界和实验证据，例如未来生效边界、旧任务恢复、防复活与实际副作用状态在同一评测中是否改善。

最新候选中 ReMe 已有 DSH 插件，EverOS、LongMemory、OpenClaw 已覆盖大量记忆治理能力。P0 必须先运行最相关候选的对照用例；满足核心契约时优先适配，后续阶段只补真实缺口。下表以需要自建权威模块的保守路径估工；若复用成功，应重估，不能机械照搬工期。ReMe 当前指南包含批量提交与仅根 agent 的默认选项，因此现成接入不等于已满足本方案的逐事件保存和子 agent 一致性要求。证据见项目全景 P38。

4 memory.json 迁移方案

4.1 迁移前准备与 dry-run

不读取凭据，不以自动扫描全部聊天作为迁移前提。通过已有合法导出或用户选定文件获取 memory 数据，在副本上运行只读检查，展示条数、类型、范围、来源、过时状态、撤销记录、无效结构和潜在 ID 冲突。

建立映射：legacy_store_id + legacy_item_id → memory_id，使用 migration_id 去重。保留 createdAt、updatedAt、source、sessionId、meta、watermarks 与 withdrawals 的原始含义；迁移时间另记，不能把所有历史内容变成今天新说的要求。

cwd 通过可信项目映射转换成稳定 project ID；无对应项目的记录先待关联，不默认变全局。缺少原始证据的自动事实标注“历史导入，证据未核验”，不能升级成用户明确要求。原 JSON 数据可能已经被截断，迁移器不能声称恢复原始完整上下文。

dry-run 只输出差异和风险报告，不写目标权威库、不改源文件。具体命令在实现后写入安装文档，本设计不提供假想的已存在命令。

4.2 导入副本和 shadow 读

导入隔离目标库，校验数量、内容哈希、作用范围、来源映射、有效状态及撤销关系。旧向量可视为可重建索引；新模型不能直接使用不兼容向量。

shadow 读表示对经过授权的同一批查询，同时在旧实现与新实现检索，正式任务仍只收到原系统结果。比较新结果的适用性、漏召回、旧信息误用、延迟和 token 量；记录可解释差异，不要求新旧结果完全一致。

shadow 阶段新服务不接收独立的用户编辑作为正式权威写入。增量变化通过旧权威提交后形成的导入事件传播，使用稳定 ID/版本去重；若旧系统没有可靠变更日志，应采用短暂冻结写入和再次全量比对，而不是承诺无缝同步。

4.3 单写入切换

选择短维护窗口，暂停记忆编辑与自动写入，确认旧插件中在途提取/向量任务已结束或取消。导出最后一致状态，完成增量导入和验证，写切换记录与最终旧版本位置。

将 UI 和模型写工具指向新服务；关闭旧插件重复的长期记忆提取、注入和同名写工具。旧插件可继续承担 DSH 内部摘要查看/编辑，但相关长期记忆事件只由新适配器写一次。最后开放写入，并验证新建、编辑、撤销、跨任务召回和重启。

原文件保存为只读迁移证据或按保留策略处理。禁止多个 agent、旧插件和新服务分别直接编辑原 JSON，再期待按时间戳自动合并。

4.4 回退与再迁移

回退前暂停新变更，导出切换后全部事件、当前视图、撤销/删除信息及迁移映射，验证操作去重。可以先回退宿主适配器版本，同时继续保留新服务为存储权威，以减少数据格式回退风险。

如果必须切回旧存储，生成经核验的兼容视图。旧格式无法表达未来生效、条件例外或删除范围时，必须列出损失并阻止相关规则降级；可保持新服务只提供这些政策，或暂时停止依赖它们的任务。不能把不兼容规则平铺成普通 note 后声称语义保留。

不能简单复制迁移前的备份覆盖当前库；那会丢失新事件并可能复活已删内容。重新迁移时沿用稳定映射，保留所有后续撤销和删除屏障。

5 决策记录

以下 ADR 是本方案拟采用的技术决策，状态为“设计选择，待原型验证”，不表示仓库已按此改造。

ADR-01 独立 TypeScript 服务，HTTP 与 MCP 共用业务层

选择。 独立进程拥有存储、事务和生命周期；HTTP 面向管理 UI 与可信宿主，MCP 提供少量模型工具。采用 TypeScript 与现有 DSH 生态一致。

理由。 服务可在 DSH 退出或容器重建后继续存在；客户端复用一致规则，降低两套接口行为不同的风险。MCP 工具不是全部产品能力，宿主仍需注入身份并管理上下文。

代价。 增加安装、进程监督、兼容版本与通信失败处理。第一版由明确的数据目录、健康状态和幂等请求控制复杂度，不立即引入多服务编排。

重新评估条件。 核心数据处理出现不可接受的运行时瓶颈，或选定数据库依赖在目标平台无法稳定部署；先测量再决定局部换语言。

ADR-02 本地权威库采用 SQLite，集中控制变更

选择。 SQL 保存原始事件引用、版本、关系、状态、收据和 outbox；主服务是唯一写入入口。使用 SQLite 本地文件，配置事务和持久化要求。

理由。 当前规模假设下部署简单，关系与版本可以在同一事务提交。禁止客户端直接打开跨机器共享数据库文件。

代价。 单写者和单机可用性限制，需要备份、恢复和明确的写入排队。直接文本编辑改为导入变更流程，牺牲随意覆盖文件的便利，换取可检测的冲突。

重新评估条件。 实测写入排队、恢复目标或高可用需求无法满足，再迁移 PostgreSQL；容量门槛由真实负载决定，不凭记录条数拍板。

ADR-03 全文检索先行，向量可选

选择。 SQL 精确过滤加 FTS5 提供默认查找；中文分词需要单独验证。向量是可重建索引，先允许小集合精确检索，sqlite-vec 等库锁定版本后再验证平台和过滤能力。

理由。 让本地无模型条件也可保存和查找；约束不依赖向量召回。初期能清楚测量 embedding 和重排带来的额外收益。

代价。 首版语义泛化有限；关键词不匹配可能漏召回。提供来源展开与改写查询，同时用基线测量缺口，不把加向量视为自动解决。

重新评估条件。 真实查询显示语义检索明显改善且成本可接受，再启用向量默认路径；多租户检索规模扩大时评估 pgvector 或独立向量服务。

ADR-04 关系先用 SQL 表，不先部署图库

选择。 用明确的 replaces、exception_to、derived_from、depends_on 关系表达生命周期与证据依赖；查询先控制深度和结果预算。

理由。 当前最关键的是规则替换、例外与删除传播，不需要一开始自动构建通用知识图谱。关系与版本同事务写入更容易核验。

代价。 大规模多跳查询可能需要额外优化；关系抽取错误仍会影响结果。

重新评估条件。 消融证明多跳检索有稳定收益且关系表成为瓶颈时，再引入图服务作为查询投影；不能让它成为第二份独立权威。

ADR-05 提取器提出变更，服务负责提交

选择。 模型输出带原文证据的结构化提案；服务验证身份、范围、来源、时间、目标版本与操作资格。明确、目标唯一的已授权变更自动提交；不确定内容保留 hypothesis 或待确认身份。

理由。 JSON 格式正确不等于语义正确。正则可做格式处理，不负责判断撤销对象；隐藏思维链不作为存储证据。

代价。 需要可标注案例、语义校准和少量用户确认；纯模型自由写库更简单，但难以获得所需变更可靠性。

重新评估条件。 模型版本变化或新领域引起误设/误删升高，重新校准而非放宽全部校验。

ADR-06 撤销、彻底删除和归档分别实现

选择。 撤销结束适用期；归档改变普通背景检索优先级；彻底删除先阻断读取，再清理服务控制的副本和备份。审计外壳尽量不含正文。

理由。 用户不再要求某行为，不等于要求禁止它，也不等于删除全部历史。删除操作必须可查看进度，恢复不能带回已删内容。

代价。 引入依赖清理、删除清单和备份期限；宿主或外部 provider 副本可能不在控制范围。

重新评估条件。 某些部署要求更强磁盘清除或加密密钥销毁，应独立定义并验证删除承诺，不能把普通 SQL delete 当成保证。

ADR-07 当前约束单独编译，受控动作重新检查

选择。 约束路径按身份、范围和时间确定性加载；背景路径进行检索。收据记录版本与时效，租约/fence 约束恢复后的旧执行者。

理由。 单纯 top-k 检索和更新通知无法保证旧上下文不会指导下一次操作。未来生效时间也可能在没有新写入的情况下改变规则。

代价。 需要宿主和工具入口配合；风格等自然语言要求不能全部形式化，必须披露保证强度。动作已被接受或已发往外部后的取消只作尽力处理。

重新评估条件。 网关覆盖不足时降低宣称的保证范围；不要通过文字提示把未接入动作包装成受控动作。

ADR-08 云端阶段使用 PostgreSQL，保持业务语义

选择。 云端、高并发多主机写入或高可用需求成立后再采用 PostgreSQL；保留 memory ID、操作语义、幂等收据、expected_revision、epoch、时间区间和删除作业接口。

理由。 存储后端变化不应让用户的“撤销”在云端变成另一种含义。先稳定接口与语义测试，再替换数据库适配。

代价。 两种后端的隔离级别、锁、全文检索和时间处理并非天然等价，必须运行同一组语义与故障测试；不能承诺复制 schema 即可迁移。

重新评估条件。 出现真实团队需求和部署预算后再启动，不以“未来可能需要”为由提前维护两套生产后端。

ADR-09 采用开源组件，以固定版本证据决定范围

选择。 复用 DSH 接入与 UI；把 Mem0、Letta、Graphiti、Cognee、文件式记忆等作为对照、算法参考或独立适配候选，不同时堆叠为四份记忆权威。具体项目事实见开源项目调研。

理由。 生命周期规则必须由一个系统解释；多套自动更新/删除策略叠加会增加不一致和评测混淆。

许可处理。 本地 DSH core、memory-lite 和根仓库文件声明 MIT，详见代码审查。拟采用的每个外部版本分别记录源码 LICENSE、依赖许可、分发方式与 NOTICE；模型权重和托管 API 条款单独核对。调研时仓库证据不代表未来版本不变，也不构成法律保证。

6 差异验证与避免过早扩张

评测应同时包含传统长对话 QA 和完整生命周期任务。单次回答正确率不足以证明项目约束稳定：还要测修改后传播、旧来源重放、并发编辑、离线子任务、未来生效边界、备份恢复和外部副作用核实。

先比较以下可解释版本：近期上下文加文件/关键词、普通向量检索、结构化版本记忆、再加入上下文收据与动作检查的完整方案。逐项移除时间模型、关系补全、辅助模型或执行校验，观察哪些机制实际贡献收益。不要只和一个没有状态过滤的弱 grep 基线比较。

提前登记指标：误设约束、误删、过时信息误用、作用域误用、撤销后新动作误接受、恢复成功、任务完成质量、完整 token/费用、P50/P95 延迟、首次成功与手工纠错时间。模型、提示、数据与评价者版本固定，区分开发集调参和保留测试集。

已有论文、预印本和项目包含撤销与生命周期评测，因此预期新意应写成“待验证假设”：把稳定身份、双时间、删除屏障、上下文收据、任务租约及受控动作边界协同起来，是否在相同成本下改善真实多 agent 项目可靠性。若实验未证明，仍可作为工程产品贡献，但不能宣称首创机制或保证精度不下降。

暂缓通用图库、训练记忆策略、多地域多主、全量历史自动采集和每次检索都启动辅助 agent。只有某类失败在数据中反复出现，且新机制有对照收益时才扩大范围。

7 启动实施前的检查清单

  • 确认目标平台、宿主版本、单用户/团队边界和可控工具范围。

从已有项目中提取的设计决策

下面是本报告的工程判断，尚需实现和实验验证。

  1. 先定义权威记录与派生索引。 SQL 事件、明确约束及来源记录应有稳定 ID 和版本；全文、向量、图和摘要可作为可重建投影。采用 Markdown 为权威源同样可行，但必须定义文件修改如何进入事务、冲突和失败如何恢复。EverOS 是后一方向的重要对照。
  2. 把“用户说了什么”“模型推断什么”“当前必须遵守什么”分开。 标签适合查询筛选，不能单独决定谁有权覆盖约束。抽取 agent 提交候选事实或变更，明确的生效、撤销与作用域由服务处理；反思结论保留其推断身份。
  3. 避免只用向量相似度和最新时间戳裁决。 相似句可能是另一项目、另一时间条件、引用或否定。应先明确对象、作用域、权限、来源、有效时间和变更关系，再用语义匹配辅助识别候选。
  4. 把可见编辑体验作为第一阶段功能。 支持查看原文依据、当前有效规则、替换关系与最近取回原因；用户可编辑并看见结果。需要重点验证手工删除如何影响原文、摘要、向量、缓存和其他 agent 已拿到的上下文。
  5. 不要从 README 的完整程度推导可靠性。 MELT 和 MemoryStackBench 已覆盖多种生命周期问题；用它们做共同基线，再增加当前工作站的容器崩溃、并发编辑、重复事件、撤销后迟到写入、跨 agent 缓存失效和恢复测试。
  6. 创新主张应限定到实验能证实的增量。 例如特定的约束版本协议、可编辑文件与事务状态的一致性保证、可执行的撤销传播契约、面向真实宿主的低配置接入。在没有检索到完全相同实现、也没有基线实测的情况下，仍不能声称这些方向首次出现。撤销、治理、可解释性本身已有相关系统和研究。

5. 可以验证的 8 个增量假设

以下是待实验验证的候选贡献。没有一个在这里被认定为首次提出；最接近的先例必须成为对照。优先价值在中文真实项目数据、DSH 集成、故障证据和统一评测，而不是重新命名已有构件。

H1 · 中文口头约束的意图、范围与授权归属

假设： 在真实中文口头修改指令上，带原文证据和显式操作类型的解析器，能以可接受的澄清率降低误撤销和跨范围覆盖。

  • 最近先例： R02、R04、R24、R40。
  • 候选增量： 增量候选是公开、人工标注的中文项目约束数据及错误分析；结构化抽取、标签或生命周期本身不主张首次。
  • 实验： 构造并人工双标确认、假设、引用、取消要求、明确禁止、仅当前任务例外、替代及彻底忘记等最小对照；按项目和表达者划分训练／测试。比较通用记忆抽取、规则模板、结构化模型与证据约束版本。
  • 指标： 操作类型准确率；错误撤销率；跨范围覆盖率；应保留事实召回率；必要澄清率与额外 token。
  • 什么结果会否定这项主张： 若优势仅来自更多模型调用，或在相同预算下不优于现有抽取器，不能称为新的方法贡献。

H2 · 撤销、在途 agent 与行动边界的联合一致性

假设： 在本地 DSH 多 agent 流程中，将权威版本、衍生来源失效和执行前新鲜度检查联合实现，可以减少撤销后的错误动作，并保持合法替代授权可用。

  • 最近先例： R25、R36、R37、R38。
  • 候选增量： 候选增量是完整运行环境中的端到端证据、故障模型和工程集成；guard、授权图、写回复活和多角色传播已有直接研究。
  • 实验： 让 agent 读取旧规则后暂停，再撤销或替代；注入事件延迟、索引落后、重试、旧摘要写回和多路径授权。与 R36 风格 guard、R38 风格授权目标计算、R37 有界授权及其合理组合比较。
  • 指标： 撤销生效后执行旧规则的次数；撤销可见延迟的 p50／p95／p99；合法行动误拦截率；写回复活率；收敛时间。
  • 什么结果会否定这项主张： 若只比无撤销检查的朴素基线好，或无法证明实际动作已被拦截而只是答案改变，不支持该增量。

H3 · 人工编辑、派生索引与崩溃回放的一致性

假设： 一个权威事实源加事务事件投递、版本校验和可重建派生索引，在用户编辑与容器崩溃交错时，能保持已确认变更的一致性。

  • 最近先例： R25、R36、R40。
  • 候选增量： 属于可复现系统整合和故障评测候选；数据库事务、事件投递和版本控制不是新的发明。
  • 实验： 经 UI 或受控文件导入修改记忆，在权威写入、回执、索引重建和导出各边界终止进程；注入重复事件、乱序事件及双人编辑。比较有无版本校验和可靠事件投递。
  • 指标： 已确认事件丢失数；重放后权威状态哈希一致率；检索返回已失效版本的比例；重复副作用数；人工冲突处理负担。
  • 什么结果会否定这项主张： 若只能在正常关闭或单写者下成立，不能宣称解决沙盒突然终止和多 agent 稳定性。

H4 · 有预算的证据展开与原子事实检索

假设： 按任务补回原子记忆的父段落和来源证据，能在固定上下文预算内提高否定、条件和时间细节的使用正确率。

  • 最近先例： R09、R14、R24、R34、R35。
  • 候选增量： 待检验点是选择何时展开及在项目任务中的预算效果；父子块、上下文化向量和多层检索已有先例。
  • 实验： 保持同一模型、语料与预算，比较固定分块、原子事实、late chunking、父子块、文件搜索及按需证据展开；增加跨句指代、例外条款、相似旧版本和隐含需求。
  • 指标： 必要证据召回率；条件和否定词遗漏率；实际任务成功率；引用支持率；总上下文 token。
  • 什么结果会否定这项主张： 若固定窗口或文件基线以同样成本达到相同效果，不能把更复杂流程算作有效改进。

H5 · 写入和后台整理的总生命周期成本

假设： 以复用率和更新频率决定何时做辅助整理，在一定查询复用区间内可降低总成本而保持任务质量。

  • 最近先例： R02、R22、R24、R28。
  • 候选增量： 贡献候选是可测的触发策略和成本交叉点；多一个 agent 必然省 token 不是已成立结论。
  • 实验： 系统改变每条记忆查询次数、更新频度、任务跨度和闲时计算预算；对照同步提炼、全部后台提炼、检索时整理及自适应策略。
  • 指标： 写入加维护加查询加回答的累计 token／费用；嵌入与重排调用数；冷启动和热查询延迟；任务质量；预处理失效率。
  • 什么结果会否定这项主张： 若节省仅来自排除后台成本，或只有超出目标使用量的高复用场景才回本，必须缩小适用范围。

H6 · 项目范围隔离与可审计的有限协作

假设： 在用户预先允许的授权策略内，以确定性范围检查和短期窄授权支持协作，可以减少无关上下文，同时维持跨角色任务成功率。

  • 最近先例： R25、R37、R38。
  • 候选增量： 增量候选是 DSH 工作流及可复现的效用／隔离联合评测；ACL、临时授权和委托图本身不是新颖机制。
  • 实验： 比较固定角色隔离、所有已授权材料全量可见、确定性窄授权协作；加入共享合法路径和撤销一个授权路径的场景。不得用模型自称需要作为超出用户策略的授权来源。
  • 指标： 任务成功率；未授权材料被送入模型的次数；无关上下文 token；授权请求数与处理延迟；合法共享路径误撤销率。
  • 什么结果会否定这项主张： 若减少 token 的代价是无法完成常见跨角色任务，或依靠放宽真实权限，不能称为同等质量的效率改进。

H7 · 计划、尝试、工具成功和验证完成的证据分型

假设： 把工作记忆中的完成状态绑定到工具回执与独立状态证据，可以降低崩溃恢复后误报完成和重复执行。

  • 最近先例： R27、R29、R31、R39。
  • 候选增量： 候选增量是动作状态证据模式与持久化联合故障实验；区分事实与观点已有研究，不能仅靠字段名称主张原创。
  • 实验： 在工具执行前、执行成功但回执丢失、回执已存但验证未完成等位置终止会话；以真实文件、数据库和工具最终状态为独立判定依据。
  • 指标： 假完成率；遗漏行动率；重复副作用数；恢复到正确状态的时间；需要用户确认的歧义数量。
  • 什么结果会否定这项主张： 若只依据 agent 自报日志评分，或完成事实仍可由摘要自行升级，实验不足以支持可靠性声明。

H8 · 槽位和类型错误下的生命周期鲁棒性

假设： 在槽位含混、日期不完整和标签误判时，保留冲突证据并延迟破坏性替代，比直接按最高相似度或最新入库覆盖更能保存正确状态。

  • 最近先例： R03、R22、R24、R40。
  • 候选增量： 重点是人工验证的噪声集、语义误合并分析和保守策略代价；双时间、状态掩码与类型本体均已有先例。
  • 实验： 对同一人物多地点、多宠物、多项目规则、相对时间和未来计划注入类型及槽位噪声；拆开比较通用生命周期、额外类型、冲突保留和语义判定模块。
  • 指标： 误失效率；过时信息误用率；冲突解析精度；人工处理负担；对标签错误率的敏感曲线。
  • 什么结果会否定这项主张： 若收益在人工正确标签下才出现，或只是以大量拒答换取低误删，需要报告代价，不能宣称精准自动判断。

6. 统一评测协议

1. 基线与公平预算

至少比较全上下文／近期窗口、MD 加文件搜索、SQL 全文搜索与确定性过滤、纯向量、混合检索无辅助模型、混合检索有辅助模型。再选 Mem0、SimpleMem、MemOS／Graphiti 或可复现的论文兼容实现。锁定模型、embedding、数据版本、代码提交和硬件；有意调大预算的版本单独报告。

2. 评测层次

分开记录原文保存与抽取保真、事实和版本正确性、检索证据覆盖、答案支持、真实任务完成、授权和撤销、延迟与总成本。最终答案正确不能代替真实工具行为正确；向量召回率也不能代替任务成功率。

3. 数据组合

LoCoMo 与 LongMemEval 测长期问答和更新；LOCOMO-CONV 测隐含需要；MemoryArena 测会话间行动依赖；LongMemEval-V2 测环境经验。MemoryAgentBench 补充增量交互与选择性遗忘能力；另做中文口头约束、人工编辑、崩溃、并发、撤销与派生数据重新写回的联合场景。

4. 划分与统计

按项目、用户或工作流划分训练、开发和测试集，防止同一事件的相似表述泄漏到两侧。公开数据哈希、排除类别、失败样例和提示版本；重复运行并报告置信区间，按任务聚类估计，不把一段对话的每条查询当完全独立样本。

5. 最小必要消融

逐项去掉标签、时间、原文指针、原子提炼、重排、辅助模型、版本验证和行动前检查，观察边际收益。特别把生命周期状态的收益与语义类型标签的收益拆开，避免组合提升全部归功于其中一个构件。

6. 硬约束与在途状态

当前硬约束和权限通过确定性路径检查，不能依赖 top-k 恰好召回。撤销后已送进模型的文本无法靠删除数据库物理撤回；测重新构造上下文、停止旧运行或行动门控后可实现的实际行为保证。

7. 成本口径

统一计入原文提炼、增删改判定、嵌入、索引维护、后台合并、查询改写、重排、回答、失败重试以及人工处理；分别报告在线延迟和累计费用。不要跨论文直接比较不同模型、基准子集和计费范围的营销倍率。

8. 可审计记忆内容

保存用户原话、公开工具调用与回执、来源定位、显式结构化操作和简短决策摘要。正则只做格式检查，不把隐藏思维链当存储接口或可靠证据。

7. 研究定位与尚未完成的验证

建议暂定定位为：面向本地多 agent 项目的可审计外置记忆集成，并用联合故障场景验证时效、撤销、编辑和真实任务完成。 这是一项研究与工程方向描述，不是原创性保证。R25、R36、R37、R38、R40 尤其需要在任何对外研究主张中正面比较。

1. 结论

当前仓库已经拥有一个可工作的轻量记忆原型，尤其在“来源对话发生编辑后，撤回先前自动提取的记忆”“记录哪些记忆已经进入模型上下文”方面，已有可继承的实现。新方案适合建设为独立记忆服务，通过 MCP 暴露模型工具、HTTP 提供管理与宿主接口，再由 DSH 原生插件承担可信身份绑定、必需约束注入、记忆使用回执及执行前检查。

现有插件不应被描述为已经具备完整的跨 agent 约束一致性：其自动提取、摘要存储与注入跳过 subagent；数据以 JSON 保存；人工编辑和删除的传播范围有限；本机 HTTP 访问防护不是逐 agent 的授权。具体证据如下。

3.1 写入与提取

  • compaction/summary 事件会保存顶层会话摘要；同一会话未钉住的旧摘要被替换，钉住的保留。自动存储不包含 subagent。见 index.js、摘要替换。
  • 自动事实提取在 agent/status = idle 后触发，使用该会话的实际模型路由；按已完成的用户轮次和 watermark 判断是否需要提取；提取期间源对话版本变化则丢弃结果。见 提取过程、版本检查。
  • 提取结构目前只有 {text, global}，最多 8 条、每条 300 字符；包含文本截断和 bullet fallback，按 token Jaccard ≥ 0.8 去重。它尚未显式表达约束主体、条件、例外、否定、来源证据片段、生效时间、替代对象。见 抽取指令与解析、去重。
  • memory_note 允许模型选择 workspace 或 global，按执行会话 cwd 保存；工具描述要求用于用户请求记住的内容或长期决策，但执行层未看到独立的“是否获准写全局”策略检查。见 工具实现。这不等于用户存在越权访问，只说明此处尚不是多租户授权层。

3.2 存储与持久性

  • 默认数据在 DSH_HOME/memory/memory.json，向量在 vectors.json；DSH_HOME 可配置，默认 ~/.dsh。它们位于应用数据目录，是否在沙盒之外取决于实际部署挂载方式，路径名称本身不能提供保证。见 路径定义、文件定义。
  • 主存储包含 items、watermarks、withdrawals，使用临时文件写入和 rename。memory.json 与 vectors.json 各自写入，代码没有把两者放在同一个事务中，也未看到此写入函数显式执行文件和目录的持久化同步。见 writeAtomic、两个保存函数。因此不能把“返回成功”扩大为对突然断电的完整保证。
  • 保存前检测磁盘修改并按 ID、updatedAt 合并；内存中本次尚未保存的删除用集合阻止同次合并复活。这个集合在保存后清空，并不是跨实例、长期保留的删除墓碑。见 合并与清理。README 明确指出：在 1.5 秒轮询窗口里由外部手工删除的记录，可能被下次保存加回。见 README 的文件语义。
  • session-source-extras.json 另存插件元数据，按稳定 message ID 关联，支持 fork lineage；其写入有独占锁。这与 memory 主存储的保存机制不同，不宜混为“全部已有跨进程事务锁”。见 sidecar 说明与位置、记录方法。
  • 向量生成使用进程内 Promise 队列；查询向量等待上限 2.5 秒，失败返回 lexical 路径。异步向量写回目前按 ID，没有 content_hash + embedding_model_revision 的条件提交。静态推导：在向量请求尚未完成时编辑或删除记录，需要防止旧向量回写。见 embedding 队列。

3.3 召回与注入

  • 范围是 global 或 cwd 路径精确归一匹配；路径统一小写并替换分隔符。尚无稳定 project ID、组织、任务、agent 角色等独立维度。见 visibleIn。迁移到 Linux 或容器路径变化时，需要重新定义项目标识和路径映射。
  • 检索为 BM25 与可选 cosine 混合，附带 pin、同工作目录和时间加分；向量与词法可以分别满足召回门槛。见 rank。这属于相关性排序，不是约束优先级或事实冲突消解。
  • 首轮加入钉住与相关项，后续主要加入未在该 session 注入过的相关项；注入有字符预算。通过事件/sidecar 判断内容是否实际进入会话，避免未落地的调用错误消耗“已注入”标记。见 pre-step、memory_recall 回执。
  • 重要约束目前仍可能因 topK、预算或仅首轮 pin 策略缺席；代码没有“当前全部适用硬约束必须被编译并装入”的独立路径。

3.4 编辑、撤销与删除

  • 编辑来源对话会把该会话之前自动抽取/压缩的记录标记为 stale，连 pinned 项也停止自动召回；已有来源元数据支持再次提取时水位重置。见 invalidateSource。这是有价值的现成基础，但范围是 session 级自动记录，未细化到具体证据跨度。
  • 已进入其他会话的失效记忆会在下一步收到可重放的撤回或纠正通知；即使关闭新 recall 注入，通知分支仍先执行。但插件被禁用时整个分支跳过，subagent 也跳过；sidecar 无法写入时通知保留待发，原运行继续。见 分支与通知。因此通知是最终传播，不是执行前强一致检查。
  • 普通记录的首次编辑/直接删除，不应被宣称已经全面传播。 文本编辑分支只在旧记录已 stale、已有 withdrawnRecall 或 withdrawals 时创建纠正记录；直接删除仅调用 remove。remove 删除 item 和向量并记录本轮删除 ID，不创建新的 withdrawal。静态推导：普通有效 note 已被另一个会话使用时，首次改字或直接删除，现有通知机制不必然通知该会话。见 编辑条件、删除路由、remove。需在实现阶段用聚焦测试确认和修复，不属于本次已修改内容。
  • withdrawals 保存旧文本前缀和纠正文本；旧 append-only 会话仍保留；无自动到期或清除 API。因此当前 delete 是活跃集合删除，不能称为物理清除。见 README 保留限制。
  • 压缩摘要编辑通过 agent.runMaintenance 追加真实 compaction 事件，检查忙碌、活动 turn、当前 checkpoint 和 token meter，成功后 flush。不会直接重写原 session 文件。见 editSummary。这套方式应继续保留在 DSH 适配层。

3.5 UI 与访问控制

  • launcher 已有搜索、pin、范围切换、编辑、删除、导入导出、清理；请求未携带记录版本。见 UI 操作。并发人工编辑适合增加版本冲突提示与差异比较。
  • launcher 将 /api/memory/* 代理到插件；当前页面依赖 DSH 已运行。见 代理。独立服务可以解除这个运行依赖，同时保留页面交互习惯。
  • 插件路由检查 loopback Host、Origin、fetch-site 和 JSON Content-Type，并允许其他 loopback origin。见 路由防护、共享 fence。这是本机 Web 请求防护，不校验组织身份或某 agent 可读写的项目；管理页 GET items 不带 cwd 时列出所有内容属于本机管理用途，不适合直接暴露为多租户数据接口。

4. MCP、hooks 与 subagent 的接入现实

4.1 MCP 适合工具互通，但不会自动解决身份传播

core MCP 客户端支持 stdio 与 Streamable HTTP，只桥接 tools，尚不支持 MCP resources/prompts。HTTP 服务必须独立运行；DSH 不负责数据库初始化、迁移、供应商账号或 HTTP 服务监督。见 指南、客户端 README。

当前调用代码发出 tools/call 的工具名与模型参数，HTTP 连接使用配置中的固定 headers；没有在这里自动附带可信 session/task/agent 标识。见 callToolUncached、transport。所以“参数里有 project_id”不能直接成为授权依据。

建议接入方式：

  1. 原型可采用单用户、单项目绑定的 MCP 连接，服务端凭连接身份限制项目；模型只能缩小搜索范围，不能扩大权限。
  2. 多任务使用 DSH 原生适配器，由真实 exec.agent.session 和可信项目注册表确定 subject/scope，向记忆服务兑换短期任务凭证；凭证不进入模型文本。
  3. 通用 MCP 客户端若需要共享同一服务，可在宿主侧提供每任务绑定的 MCP 代理；代理添加身份并过滤能力，服务端仍再次检查。不得依赖模型自行填报角色标签。
  4. 配置客户端超时与故障状态提示。重连只解决连接恢复；超时的变更必须用同一幂等键查询/重试，不能把重新连上当成操作未执行。

4.2 hooks 适合观测和兼容，关键约束更适合原生扩展点

现有 Claude Code bridge 能在 agent/pre-step、tools/pre-execute、tools/post-execute 等时机增加上下文或阻止工具，但 README 明确列出兼容限制。SessionStart 是 detached，可能错过首个模型请求；某些错误继续运行；部分输入输出字段会被简化。Codex bridge 未支持 subagent hooks，Claude bridge 的 subagent start 只尽力投递到仍活着的进程内子任务。见 Claude hook 映射、Claude 限制、Codex 限制。

因此：hooks 可以实现初期事件采集与提示，不能单独作为“首请求前全部约束生效”“所有工具动作都经过授权”的保证。完整接入用 DSH 原生插件在请求构建前等待约束快照，在具体受控工具的执行器中检查权限和版本；对无法语义验证的自然语言限制，仍只能提供提示和后验检查，不能声称硬保证。

4.3 与 core 的日志和生命周期约束配合

core 要求模型可见内容可以从 session 日志重建，新输入要有 session event；扩展行为优先走插件而非修改 agent-loop。见 core 约定。现有 sidecar 正是为了避免把未文档化字段塞进受版本校验的 user/message.source。新适配器宜使用正式定义的 memory/context-attached、memory/context-revoked 等事件或严格兼容现有 sidecar；不能随手增加 source 字段后假设旧日志迁移仍工作。

子 agent 核心已有持久化 descriptor、父子相邻权限、cold resume、inbox 与停止前复查等生命周期实现。应把外部记忆租约关联这些真实身份，避免另造一套互相矛盾的 agent 名册。见 continuable flow、ownership。外部服务的租约不应替代 core 的生命周期，只管理记忆快照与授权有效期。

6. 渐进集成路径

阶段 A：独立单用户服务与可见管理

实现 SQL 记录、版本、来源、完整命题、作用范围、撤销、变更提案及简单全文搜索。先允许手工记忆和明确的“请记住”工具，不强依赖 LLM 提取。服务由自己的进程/容器运行，数据目录显式挂载到持久卷；DSH 只连接它。先用语义最简单的检索与过滤证明生命周期可靠，再增加向量。

阶段 B：现有 JSON 导入与并行评估

增加只读导入器，将旧 ID 映射为新稳定 ID，保留 source、sessionId、scope、cwd、createdAt、updatedAt、meta、withdrawals 与来源版本。对没有原始证据的旧事实标记“历史导入，证据未验证”；不能自动升级为用户明确规则。旧路径转换为 project ID 要通过项目注册表完成，不能仅按文件夹名字猜。

导入后进行数量、状态、文本哈希与撤销关系校验，先做只读对照检索。导入器需有 migration_id + legacy_id 幂等约束；重新导入旧备份不能覆盖新的撤销或 purge 状态。向量是派生数据，允许重建；为可比性可以记录旧模型和来源，但不要把旧向量维度当成新模型可用。

阶段 C：DSH 原生适配器与 launcher 切换

保留 UI 的搜索、编辑、pin 等交互，后端代理转向独立服务；新增“撤销要求”和“彻底删除”两个明确动作，以及版本冲突、来源、影响任务、撤销进度。修改保存携带 If-Match 或 expected_version。

在当前 agent/pre-step 集成点构建正式约束上下文和回执；在 session/event 收集已获准的持久事件；利用实际 exec.agent.session 确定身份。切换时只保留一个写入权威：旧插件可留作摘要查看/编辑宿主，但关闭与新服务重复的自动提取、长期记忆注入及同名写工具。不要长期双写两个可编辑权威库。

阶段 D：多 agent、容器恢复与执行检查

接入子 agent 创建/恢复事件、短期范围凭证、scope epoch、撤销游标与执行器检查。恢复前重新取当前权限和当前约束，不恢复旧凭证。将后台提取和向量生成放入持久任务队列，任务携带输入版本和内容哈希；旧任务结果在提交时失效。

迁移回退应通过新服务导出一个经验证的兼容视图再切回旧服务，保留迁移以来的变更；简单恢复旧 JSON 会丢失新记忆并可能复活已删内容，不作为默认回退方式。

7. 可靠性红队：必须设计与验收的 12 项

场景 必须具备的机制 最小验收案例
1. 两个 agent 同改一条规则 乐观并发版本检查；无条件覆盖不得作为更新默认值；冲突显式保留 A、B 均读 v7，A 提交 v8；B 基于 v7 提交返回冲突，不能静默覆盖
2. 网络超时后重复提交 幂等键与 operation 状态；事务提交结果可查询 服务已提交但响应丢失，客户端同键重试仍只有一条变更和同一 operation ID
3. 索引更新与数据库提交之间崩溃 事务 outbox/持久任务；向量按内容哈希、模型版本条件写入；读后核验活跃版本 v2 提交后进程崩溃，重启能重建索引；v1 的延迟 embedding 不得覆盖 v2
4. 撤销发生在检索后、工具执行前 scope epoch、执行前检查、陈旧上下文刷新；关键机器政策由执行器强制检查 检索得到允许上传，用户随后撤销，旧快照不能启动新的上传动作
5. 已运行/离线 agent 继续使用旧记忆 持久撤销 cursor、租约到期、必要动作 fail-closed、恢复重新取快照 离线 10 分钟的子任务重连后先刷新；不能先完成写操作再补通知
6. 旧聊天或备份重新提取使规则复活 变更关系、撤销/删除屏障、导入 generation 检查；来源处理版本 撤销规则后重新导入旧备份并重跑提取，默认检索仍不恢复旧规则
7. purge 后派生副本残留 删除任务清单、依赖图、索引/缓存/摘要/证据处理、备份保留声明 删除原始消息后，相关事实/向量/摘要不再可检索；UI明确已控制与未控制副本，不伪称全网清除
8. 磁盘写失败、进程被终止或突然断电 明确提交/确认点、合适持久化配置、完整性检查与恢复流程 在每个提交阶段注入故障；仅已确认持久化的事件承诺恢复，未确认事件可幂等重传
9. 工具已产生实际副作用但结果未记录 intent/started/confirmed/unknown 状态；外部幂等键与核验；不可盲目重放 文件已写或支付/部署已执行后宿主崩溃，恢复先查实际状态；不能把缺少成功日志当成未执行
10. 子 agent 租约过期后旧进程复活 单调 fencing token，由服务/受控执行器拒绝旧 token；父子身份与真实任务绑定 同一任务 generation 2 已接管，generation 1 迟到提交被拒绝，不出现双主
11. 模型伪造标签、project_id 或来源权威 可信身份注入、服务端行级范围检查、user/assistant/tool 证据分离；拒绝模型自行提权 后端 agent 参数填写 global/admin 也不能扩大凭证范围；网页文本不能变成用户禁止规则
12. 回执误记、压缩丢约束或 token 预算不足 区分已检索与实际投递、稳定 ID/版本回执；约束独立于摘要重建；完整输出预算检查 被取消的请求不标记已展示；压缩后重新装入活跃约束；约束过多时显式缩小任务或拒绝开始

额外说明：执行前检查无法撤销已经开始的不可逆动作；如果要求更严格，必须把受控动作与 epoch 检查尽可能放到同一个可信执行服务里，规定动作进入不可取消阶段后的语义。自然语言约束也无法全部编译为确定性规则，应按“可机器检查”和“需要模型理解”分别报告保证强度。
